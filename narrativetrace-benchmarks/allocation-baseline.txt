# THE AGENT'S INACTIVE PATH IS NOW FREE, and the threshold moved 400 → 64 to say so. Until
# 2026-09-01 the injected sequence built `String[] paramNames`, `Object[] paramValues` (with
# boxing) and `boolean[] redacted` on every invocation, then called `enterMethod`, which built a
# whole `MethodSignature` before asking whether tracing was on; the exits then materialised a
# `TraceStack` for a trace nobody kept. `AgentRuntime.isActive()` is now the first instruction of
# every instrumented method and every injected call sits behind it, so at OFF the method
# allocates nothing over its own work — 56 B/op, `directCall` exactly.
#
#   ARITHMETIC FOR THE NEW THRESHOLD. 56 measured + the 8-byte band this suite has used since
#   2026-08-31 = 64, which is `directCall`'s threshold, which is the right answer: an inactive
#   instrumented method and an uninstrumented one allocate the same thing, so they are gated the
#   same way. The band is 8 because the smallest regression that can exist here is one object —
#   16 bytes of header before a single field — and these rows reproduce to ±0.001 B/op.

# TWO ROWS MOVED BECAUSE OF THIS RUN, AND THE REST MOVED BEFORE IT. Read the "2026-08-31"
# column carefully: it was taken on the earlier 2026-08-31 tree, and four core changes landed between that
# commit and this run (the ring's seqlock slot protocol, the capture that waits for its own
# events, the flush-after-close fix, the one-monitor drain). To separate the two causes, the two
# benchmarks this run touches were measured at 8526a2e9 — the run's starting commit, after those
# four and before either change — with the same jars and settings:
#
#   agent_noAnnotations         2648 → 2216   −432 B/op (−16.3 %), THIS RUN
#   context_enterExit_SUMMARY   3096 → 2984   and, more to the point, the arithmetic below
#   context_enterExit_DETAIL    3008 → 2984   not this run; ±24 B of drift between runs
#   context_enterExit_NARRATIVE 3040 → 2984   not this run; same drift
#   context_enterExit_OFF        392 →  392   unchanged
#   agent_OFF                     56 →   56   unchanged (the gate landed in 3ad17721)
#
# `proxy_*`, `spring_*` and `nesting_*` exercise neither the agent call site nor SUMMARY
# pruning, so nothing in this run can have moved them; their deltas against the 2026-08-31
# column belong to the four core commits, and are recorded here rather than attributed.
#
# SUMMARY NO LONGER COSTS MORE THAN DETAIL, which is the point of the change and the one
# comparison that carries no run-to-run noise, because both halves are measured in the same run:
#
#   before (8526a2e9)   SUMMARY 3096 − DETAIL 3008 = +88 B/op
#   after  (2026-08-31)  SUMMARY 2984 − DETAIL 2984 =   0 B/op
#
# `TraceTreeBuilder.pruneSummary` used to rebuild every root at capture time whether or not
# pruning had anything to do there — two `ArrayList`s and a `TraceNode` to arrive at a tree
# identical to the one it was handed. It now returns a root whose children are already what
# SUMMARY keeps as the same instance, and the list holding it too. Nothing gates this
# relationally — `allocationCheck` compares absolute bytes per row, and SUMMARY is an active
# path — so the per-commit guard is `SummaryPruningSharingTest` in narrativetrace-core, which
# pins the sharing itself rather than its price.
#
# WHAT REPRODUCES AND WHAT DOES NOT. Both full runs agreed to the byte on every `context_*`,
# `agent_*`, `spring_*` and fast-path row; a third, narrower run of the same jars read
# `context_enterExit_ERRORS` at 2960 where the two full runs read 2936, which is why 2960 is
# recorded. The `proxy_*` rows batch 1,000 calls per invocation, so the JIT sometimes
# scalar-replaces allocations inside the loop: across the two runs `proxy_notTraced` read
# 1034.1 / 938.1 and `proxy_narrated_static` 1426.1 / 1402.1. Every figure above is the maximum.
#
# THE TIME CEILINGS IN `baseline.txt` ARE NOW CONSERVATIVE FOR THE AGENT and were deliberately
# not tightened here. `agent_OFF` reads 36.8 / 37.8 ns against a 100.4 ns ceiling, but that
# ceiling is the worst of three runs on a container that has produced ±93 % error bars on this
# very row, and two samples are not three. Tightening a time gate from a smaller sample than the
# one that set it is how a gate becomes flaky. Recorded, not done.
