# NarrativeTrace 与开发周期

[English](../lifecycle-guide.md) | [Español](../es/guia-del-ciclo-de-vida.md) | **简体中文**

NarrativeTrace 既不是一个附带生产模式的测试期工具,也不是一个碰巧能在测试里用的
生产追踪器。它是**同一套捕获机制,随着代码在周期中推进,变化的只是配置与消费方**:
同一条追踪,在开发时为单元测试充当文档,在 CI 中为构建把关,在验收运行中对已部署
环境进行叙事,在生产中流经你的日志栈。本指南依次走过三个阶段,最后浓缩为一张配置
矩阵和一份隐私立场。

各机制指南([安装](安装指南.md)、[配置](配置指南.md)、[注解](注解指南.md)以及
各集成指南)解释每个部件;本指南解释**每个部件在你的流程中什么时候发挥价值**。
想在继续阅读前先获得直观感受,可在仓库根目录运行 `./demo.sh`。

---

## 1. 开发期 — 内循环

开发期的消费方是**正在阅读的你**。追踪搭载在你本来就要写的测试上;不需要额外
插桩,也不存在任何长期基础设施。

- **零配置的测试集成。** 只要 JUnit 5 扩展在 classpath 上(由 ServiceLoader
  自动发现;JUnit 4 规则需显式声明),每个测试默认就会把自己的追踪写成可审阅
  的工件——无需任何配置,设置 `narrativetrace.output=false` 可退出 *(since 0.2.2, unreleased)*:
  `build/narrativetrace/traces/<测试类>/<test>.md`,外加规范 `.json` 和每个场景
  一张 Mermaid 图。[Gradle 插件](Gradle插件指南.md)用一个 `narrativeTrace { }`
  块完成依赖、`-parameters` 编译参数和测试 JVM 属性的全部装配。
- **失败的测试讲述自己的故事。** 测试变红时,完整的捕获追踪会作为失败叙事打印
  出来 — 调用了什么、带着什么值、停在哪里 — 都在你打开调试器之前。
- **趁便宜时获得命名反馈。** 清晰度评分读取捕获的追踪,按场景报告方法/类/参数
  的命名质量(`clarity-report.md`、控制台摘要)。在这个阶段它只是建议性的:
  是镜子,不是闸门。
- **词汇从代码中生长。** 设置 `narrativetrace.glossary=true` 后,套件把领域术语
  采集进提交入库的 `glossary.json` — 术语的整理在代码评审中进行,和其他工件一样。

这个阶段培养的习惯正是重点:**追踪是你读的第一样东西**,先于日志语句,先于
调试器。周期后面的一切都复用这份同样可读的捕获。

## 2. 测试期 — CI、集成、验收、冒烟

测试期的消费方是**机器与评审者**:构建闸门、工件归档、其他平台、AI 工具,
以及观察已部署环境的测试人员。

- **追踪作为构建工件。** 阶段 1 的按测试文件就是 CI 工件:归档
  `build/narrativetrace/`,失败的流水线自带叙事。评审者读到的是代码做了什么,
  而不是提交者说它做了什么。
- **质量闸门。** `clarityCheck` 在 `./gradlew check` 内运行:阈值
  (`clarity.minScore`、`clarity.maxHighIssues`、`clarity.maxSuiteIssues`)把
  阶段 1 的镜子变成构建闸门,`warnOnly` 是软启动模式。`clarityScan` 不运行测试
  即可为已编译类评分,供把两者分开的流水线使用。
- **机器可读的导出。** 两个 opt-in 开关扩大受众:
  `narrativetrace.canonicalJson=true` 按测试写出 schema 1.2 条目数组(其他
  实现与一致性 fixture 消费的契约);`narrativetrace.structuralJson=true`
  写出不含值的结构化工件(ADR-002 第 1 级),可以零数据暴露地交给 AI 评审工具。
- **验收与冒烟测试观察的是已部署的系统。** 在这里,追踪从测试 JVM 移入被测
  应用,提前使用生产集成:servlet 过滤器、Spring 或 Micronaut 装配,或者 —
  对无法修改的系统 — 把 Java agent
  (`-javaagent:narrativetrace-agent-<版本>-standalone.jar`)挂到部署上。冒烟
  测试于是可以对*读得懂的行为*做断言:容器日志中被叙事的请求流,靠 MDC 中的
  `traceId` 关联。WildFly 示例 `narrativetrace-examples:ejb4` 正是这个形态。
- **处处同一 schema。** 验收环境发出的规范流与单元测试相同,针对一个阶段写的
  工具在另一个阶段同样可用 — 这正是规范 schema 要保护的一致性。

## 3. 生产

生产中的消费方是**运维人员、日志工具,以及 — 在显式路由之后 — AI 系统**。
设计约束随之改变:成本、丢失容忍度和隐私占据主导。

- **作用域与成本。** `narrativeTrace { scope.set("production") }` 把库移到
  runtime classpath。捕获级别就是成本旋钮 — `OFF`(每次调用约 1–2 ns)→
  `ERRORS` → `SUMMARY` → `NARRATIVE` → `DETAIL` — 且可在运行时切换
  (`config.setLevel(...)`),所以"事故时调高叙事、事后调回"是一次运维操作,
  不是一次发布。
- **两道相互独立的闸门(ADR-008)。** 捕获级别决定记录什么;你的日志配置决定
  发出什么、发到哪里。叙事事件经 SLF4J 桥接流经 `narrativetrace` logger
  (默认 ENTRY/RETURN 为 TRACE,EXCEPTION 为 WARN),因此路由、过滤与投递靠的
  是普通的 appender 配置 — 而不是库的配置。
- **身份走 MDC,不进消息正文。** 追踪身份(`traceId`、`nt.class`、`nt.method`、
  `nt.package`)、服务身份(`service.*`,`capture.resource` 开启时还有
  host/pid/runtime)以及三层属性模型(ADR-009)都以 MDC 键呈现;可见性由你的
  日志模式或 JSON encoder 决定。
- **OpenTelemetry。** 捕获的追踪可导出为 OTel span(批量或实时监听器),与你
  现有的 tracing 并存;NarrativeTrace 从不重复发出客户端 SDK 拥有的资源属性。
- **实时派生视图都是订阅者。** 尽力而为管道(`BufferedEventConsumer`)暴露一个
  发布者接缝;一切派生物都挂在那里、在调用线程之外运行:翻译叙事流
  (`narrativetrace.i18n.<locale>` logger 或按追踪拆分的 Markdown 文件,由术语表
  驱动)和对 AI 安全的结构化流(`narrativetrace.ai.structural`,每个事件一行
  不含值的 JSON)。这条路径**在高负载下按设计有损** — 宁可丢弃也不阻塞应用。
  同步监听器路径才是持久记录;派生视图是叠加其上的便利。
- **谁启动了排空线程,谁就负责 `close()`。** 这里的每一种集成方式 —— Spring、
  Servlet 过滤器、Agent、两个 JUnit 扩展 —— 都通过 `startConsumer=false` 创建的
  消费者保留事件:没有后台线程,没有 JVM shutdown hook,没有任何东西把它作为
  GC 根。离开作用域的上下文会像任何其他对象一样被回收,未调用 `close()` 也不会
  泄漏。反过来,如果你自己构造一个带排空线程的 `BufferedEventConsumer`
  (`new BufferedEventConsumer()`,或 `(int capacity)` 形式),它注册的 shutdown
  hook 会把该消费者、它的环形缓冲区以及缓冲区保留的一切一直钉到 JVM 退出为止。
  这是唯一必须调用 `close()` 的形态 —— 用 `try`-with-resources 来写它。
- **捕获开关保持保守。** `capture.resource` 默认开启(对主机名敏感的部署可以
  关闭);`capture.sourceLocation` 与 `capture.instanceIds` 默认关闭。开关只
  控制捕获,从不改变 schema 形状 — 未启用的字段保持缺席,消费方永远不必根据
  配置分支。

## 阶段 × 配置矩阵

| | 开发 | 测试 / CI / 验收 | 生产 |
|---|---|---|---|
| **主要消费方** | 阅读中的开发者 | 闸门、工件、机器、测试人员 | 运维、日志栈、经路由的 AI 流 |
| **集成方式** | JUnit 5/4,经 Gradle 插件 | 同左,另加已部署环境中的过滤器/agent | Proxy / Spring / Micronaut / servlet / agent;`scope = "production"` |
| **捕获级别** | `DETAIL` | `DETAIL` | 基线 `SUMMARY` 或 `NARRATIVE`;按需 `DETAIL`;热点路径 `OFF`/`ERRORS` |
| **输出** | 按测试的 `.md` + `.json` + 图表,失败叙事 | 同左,作为 CI 工件;`canonicalJson` / `structuralJson`;验收时的容器日志 | SLF4J 流 + MDC;OTel span;订阅者流(i18n、结构化) |
| **闸门** | 无 — 清晰度只是建议 | `clarityCheck` 阈值、你自己对追踪的断言 | 无 — 是可观测性,不是强制 |
| **丢失模型** | 完整(测试内同步捕获) | 测试内完整;已部署 = 生产模型 | 同步路径持久;订阅者路径尽力而为,高负载下丢弃 |
| **脱敏** | **始终开启** | **始终开启** | **始终开启** |

## 贯穿周期的隐私立场

矩阵的最后一行是刻意的,值得作为规则写明:

**脱敏是无条件的。不存在任何阶段、开关或属性能关闭 `@NotTraced` 或基于名称的
脱敏规则 — 这是决定,不是疏漏**(所有者决定,2026-08-16)。理由:

- "输出是安全的"之所以有价值,在于它是一条*不变式*,而不是一种配置状态。本库
  写出的每个工件 — 测试追踪、CI 归档、容器日志、AI 流 — 都可以直接分享,无需
  先审计它产生时开了哪些开关。
- "测试数据是合成的"恰恰在关闭开关最诱人的环境里不成立:验收与预发系统例行
  灌入形似生产的数据。
- 测试工件会流动 — 进入版本控制、工单和 AI 工具。而这些正是脱敏要保护的输出。

当被脱敏的值妨碍调试时,受支持的做法依次是:对行为断言而不是对秘密值断言;
利用捕获到的**声明类型**(schema 1.2)在不泄露的前提下诊断形状;构造名字本身
就携带信息的、明显为假的 fixture(`"card-token-for-decline-path"` 会被脱敏,
但参数名和类型仍在叙事)。一条**按测试、显式注解的逃生通道**(在代码评审中
可见、只通过 JUnit 扩展接线 — 绝不经过生产配置链 — 并在它触及的任何文件里
打上醒目横幅)是已记录的设计方向,按需求门控:等真实用户撞上这堵墙时才会
构建;而全局开关永远不会构建。

还要注意脱敏并非独自承担一切:`SUMMARY` 和 `NARRATIVE` 级别抑制全部参数值,
结构化工件在架构层面剔除所有值字段,渲染值也无法伪造日志行或破坏
Markdown/图表语法(注入加固)。脱敏只是整体立场中的一层,周期的每个阶段
挑选它需要的那些层。
