# 结构化追踪格式(`.nt`)

[English](../structural-trace-format.md) | [Español](../es/formato-de-traza-estructural.md) | **简体中文**

AI 安全的结构化追踪产物(ADR-002):每个测试场景一个文件,只包含开发者写下
的行为*形状*——零运行时值。这个格式是**跨平台**的:每个 NarrativeTrace 移
植版都产出完全相同的格式,这也是审批基线与一致性 fixture 能够跨平台迁移的
原因。

## 文件与命名(跨平台决策,2026-08-24)

| 文件 | 作用 |
|---|---|
| `build/narrativetrace/structural/<TestClass>/<scenario>.nt` | 在 markdown 路径上产出;磁盘上的这个文件是**最近一次绿色运行的基线**——失败的运行会与它比较(控制台 delta、失败报告),但绝不会覆盖它 |
| `src/test/narratives/<TestClass>/<scenario>.approved.nt` | 已提交的审批基线(`NarrativeApproval`;通过 `narrativetrace.approval=true` 开启,目录可通过 `narrativetrace.approvedDir` 配置)——一个通过的测试,如果其结构与基线不同,会以可读的 diff 失败 |
| `<scenario>.received.nt` | 在审批不匹配时(或尚不存在基线时)写在基线旁边;审阅它,然后通过 Gradle 的 `approveNarratives` 任务提升它 |
| `<scenario>.incomplete.nt` | 内容相同,但在这次运行本身不完整时(尽力而为路径丢弃了事件,或在采纳上限处拒绝了一个 async 作用域)会写出这个文件而不是 `.received.nt`。`approveNarratives` 按文件名忽略它:一次不完整的运行绝不能变成已提交的基线,否则之后每一次完整运行读起来都像是*新增*了调用。这样的运行按子序列包含关系而不是相等关系来比较——缺失是被容忍并被点名的,而任何新增或重新排序的内容仍然会失败 |

格式扩展名放在最后(`.approved.nt`,遵循 ApprovalTests 的约定),这样编辑器
和 diff 查看器都能以 `.nt` 为依据识别。注意:`.nt` 在一些语法高亮映射表里会
与 RDF N-Triples 冲突;在需要的地方于 `.gitattributes` 中注册一条覆盖规则。

## 内容

```
scenario: Weekend trip settles with three transfers

- TripSettlementService.recordExpense(tripName, expense)
  - ExpenseValidator.ensureValid(expense)
  - TripLedger.recordExpense(tripName, expense)
- TripSettlementService.settleTrip(tripName) → value
  - TripLedger.expensesOf(tripName) → value
  ~ fork [2]
    - BalanceCalculator.computeBalances(expenses) → value
    - StockService.check() → value
```

- **头部:** `scenario: <humanized test name>` + 一个空行。仅此而已——没有结
  果、没有追踪 id/名称、没有日期。
- **调用行:** `ClassName.methodName(paramName, paramName)`——只有名称,按捕
  获顺序排列,每层深度缩进两个空格。
- **结果类型:** 非 void 返回记作 ` → value`;void:什么都不写(返回 null 的
  约定);抛出异常记作 ` !! ExceptionSimpleName`(类型属于结构,而异常消息是
  一个值,永远不会出现);未匹配的进入记作 ` ?? incomplete`。
- **并发:** fork 组渲染为 `~ fork [n]`;从传播的上下文快照(Spring 的
  `@Async`、Micrometer,或任何手动的 `snapshot.activate()`)采纳而来的工作
  渲染为 `~ async [n]`,二者的成员都**按 `Class.method` 排序**——跨线程的捕
  获顺序取决于调度器的选择,而不是行为本身,因此产物只表达并发工作的集合与
  嵌套关系,绝不表达其顺序。async 组按发起它们的 span 分组,因此同一次调用
  的每个 async 子项都归入同一个组;当工作比调用方存活得更久时,它们也会出现
  在根层级。即发即弃(fire-and-forget)渲染为 `~ fire-and-forget` 加上其子
  项。线程名/id 永远不会出现。
- **按设计排除:** 所有参数/返回值、异常消息、耗时、时间戳、线程身份、追
  踪/span id、追踪名称、运行结果,以及叙述(已解析的叙述会内嵌值;而叙述*模
  板*会在 `nt.narrationTemplate` 随术语表 Phase 6 落地后加入)。
- **编码:** UTF-8、LF、末尾换行。标识符会经过控制字符净化处理。

## JSON 兄弟文件中的身份标识

`.nt` 产物完全不携带任何身份标识——这正是它能做到逐字节确定性的原因。它的
JSON 兄弟文件则携带身份标识:按测试生成的 `<test>.canonical.json` /
`<test>.structural.json` 条目数组、章节信封(`chapter.schema.json`),以及章
节树文档(`chapter-tree.schema.json`,章节会把它内嵌进
`nt.chapterTree`)。这三种输出者以相同方式解析身份标识,因此一个章节绝不会
与它内嵌的树指向不同的追踪。在这三处,三个身份字段**始终存在**,无论捕获是
如何完成的:

| 字段 | 如何解析 |
|---|---|
| `trace_id` | 从传入的 `traceparent` 采纳;否则继承自捕获所运行的那条追踪;否则生成——始终是一个真实、唯一、符合 W3C 格式的 id(32 位小写十六进制,绝不会全零)。绝不是共享常量,也绝不会按条目重新生成。 |
| `nt.storyId` | 当追踪已经携带一个时继承它;否则从第一个根层级调用派生为 `Class.method`。绝不生成。 |
| `nt.chapterId` | 当追踪已经携带一个时继承它;否则等于 `nt.storyId`——即这个服务对那个故事贡献的章节。绝不生成。 |

`nt.traceName` 是从 `trace_id` 派生出的(那个三词短语),所以它与 `trace_id`
永远一致;而当没有任何来源提供 `service` 时,它会回退到
`unknown_service:java`。一棵节点丢失了 span 上下文的树——无论是手工组装
的、从产物回放出来的,还是由静态扫描产生的——仍然会作为它本来就是的那一条
追踪导出:身份属于这棵树,只解析一次,并由章节、章节内嵌的树,以及该章节的
每一条条目共享。

因此章节树文档的 `trace` 块始终携带 `traceId` 和 `traceName`。它其余的字
段——`serviceName`、`environment`、`httpMethod`、`httpRoute` 以及请求作用域
的各类标识符——只有在树确实携带了可供继承的 span 上下文时才会写出:一个生
成出来的身份标识知道这*是哪一条*追踪,却对是谁调用了它一无所知,而凭空捏造
一个服务名会比干脆省略它更糟。`chapter-tree.schema.json` 把整个块标记为可
选,而始终存在的这种形式满足这个要求;schema 是一条底线,而不是各个输出者
之间的契约本身。

因此,同一行为的两次运行会产出完全相同的 `.nt` 文件,以及*不同*的
`trace_id`。这正是刻意设计的分工:职责是分组或描述的字段是派生且稳定的,职
责是保持唯一的字段则是生成出来的(ADR-014)。跨运行或跨移植版的一致性比较,
会先把这些唯一性字段归一化,再进行比较。

## 保证

1. **确定性:** 行为相同 ⇒ 文件逐字节相同。这正是让这份产物能够充当审批测
   试基线与一致性 fixture 黄金格式的原因。
2. **不含值:** 零提示注入面,零 PII,token 最少——默认就可以安全地交给 AI
   Agent(免费层的 Level-1 输出)。
3. **分工:** 这份产物断言的是行为的*形状*;值的正确性仍然是测试断言的职
   责。一次只改变返回值、结构保持不变的改动,不会改变这份产物——这是设计使
   然。
