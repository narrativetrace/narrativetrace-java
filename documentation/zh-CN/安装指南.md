# NarrativeTrace Java 安装指南

[English](../installation-guide.md) | [Español](../es/guia-de-instalacion.md) | **简体中文**

本指南介绍如何在 JVM 项目中安装并接入 NarrativeTrace Java。

## 前提条件

- Java 17+
- Gradle 构建

## 兼容性

以下是本次发布所依据的编译与测试版本。「自带」表示模块依赖它、由 Gradle 为你解析;「你提供」表示
模块只针对它编译而不依赖它 —— 你本来就有,NarrativeTrace 使用你带来的版本。

| 要求 | 版本 | 由谁提供 |
|---|---|---|
| Java | **17+** —— 在 17 上编译与测试;JDK 21 由定时 CI 任务覆盖(虚拟线程测试只在那里运行) | 你提供 |
| Gradle(用于插件) | **8.0+** —— 针对 8.14.2 开发与测试 | 你提供 |
| JUnit 5 | 5.11.4(`narrativetrace-junit5` 以 `api` 暴露 `junit-jupiter-api`) | 自带 |
| JUnit 4 | 4.13.2 | 自带 |
| TestNG | 7.10.2 | 自带 |
| Spring Framework | 6.2.3 —— 即 Spring Boot 3.x | 自带 |
| Micronaut | 4.7.6 | 自带 |
| Jakarta Servlet | 6.0(`narrativetrace-servlet`) | 你提供 |
| SLF4J | 2.0.16 | 自带 |
| Micrometer context-propagation | 1.1.2(`narrativetrace-micrometer`;`ContextPropagatingTaskDecorator` 也需要它) | 由 micrometer 模块自带;若不用该模块而使用装饰器,则由你提供 |
| OpenTelemetry API | 1.46.0(`narrativetrace-opentelemetry`) | 你提供 |
| ASM | 9.7.1 —— 已 shade 进 `narrativetrace-agent`,不会出现在你的 classpath 上 | 自带 |

### 运行平台

上表讲的是版本;本节讲的是*库在哪里运行*。

| 平台 | 是否支持 | 说明 |
|---|---|---|
| 服务器与桌面 JVM(HotSpot、OpenJ9、运行于 JVM 的 GraalVM) | **是** | 经过测试的目标平台 |
| Android | **否** | 未经测试,而且不仅仅是"尚未测试"——见下文 |
| iOS 及其他 Apple 平台 | **不适用** | 请使用 Swift 版本 |
| GraalVM 原生镜像 | **未测试** | 代理与 agent 路径依赖反射;目前未提供可达性元数据 |

**为什么 Android 是"否"而不是"暂时还不行"。** 在 R8/ProGuard 混淆下,有三处机制会
*静默*降级:SPI 发现会丢失 `META-INF/services` 条目,扩展因此永远不会加载;流水线
引导按名称解析 SLF4J listener,同步叙述因此消失;而值渲染依赖对字段与 getter 的反射,
叙述因此会显示为 `→ a.b(c: "x")` 而非可读的名称。三者都不会显式报错,这使得"在调试
构建里看起来能用"成为最糟糕的结果。诚实的 Android 支持需要随包发布的消费者 keep
规则以及真正的 Android CI,而这两者目前都不存在。`narrativetrace-agent` 在那里永远
无法工作:Android 没有 `java.lang.instrument`。

在缺少 `java.lang.ProcessHandle` 的运行时上,本库不再*崩溃*(进程 id 直接报告为缺失,
schema 允许这样),但不崩溃并不等于受支持。

插件在应用时就会强制前两行:不受支持的 Gradle 版本、或目标 Java 低于 17 的构建会
立即失败并写明要求,而不是稍后在库内部失败。

有两种失败值得点名,因为它们的报错都不会指向真正的原因:

- **参数名变成 `arg0`、`arg1`** —— 缺少 `-parameters` 编译标志。这是硬性要求,
  不是可选项;见下面的第 1 步。
- **运行时 `NoClassDefFoundError`** —— 运行时 classpath 上缺少某一行「你提供」的
  依赖。这些模块刻意只针对相应 API 编译,好让不用 servlet 或不用 OTel 的应用
  不必背上额外依赖。

## 使用 Gradle 插件快速上手

Gradle 插件会自动处理所有接线工作——依赖、编译器参数以及测试 JVM 配置。

在 `pluginManagement` 中把 Maven Central 放在前面 —— 插件及其 marker 每次发布都会推送到
Maven Central,而 Gradle Plugin Portal 的收录要等 Gradle 批准新的插件 id,所以让一个刚发布的
版本当天就能被解析的是 Central:

```kotlin
// settings.gradle.kts
pluginManagement {
    repositories {
        mavenCentral()
        gradlePluginPortal()
    }
}
```

```kotlin
plugins {
    id("ai.narrativetrace") version "0.5.0"
}
```

就这么简单——也不需要额外的 JUnit 依赖：在 `testFramework = "junit5"` 下,插件会把 Jupiter 引擎加到 `testRuntimeOnly`,因为它所配置的 JUnit Platform 没有引擎就拒绝启动。运行 `./gradlew test`,追踪输出就会出现在 `build/narrativetrace/` 中。

若要强制执行命名质量阈值：

```kotlin
narrativeTrace {
    clarity {
        minScore.set(0.80)
        maxHighIssues.set(0)
    }
}
```

现在，只要任何场景的清晰度评分低于 0.80，或存在任何 HIGH 严重级别的问题，`./gradlew check` 就会失败。

完整的 DSL 参考、拦截模式、模块级启用以及配置范例，请参阅 [Gradle 插件指南](Gradle插件指南.md)。

## 手动配置

以下各节介绍不使用 Gradle 插件的项目的手动安装方式。

### 前提条件

- 已启用编译器参数元数据（`-parameters`）

## 1. 启用参数名称保留

NarrativeTrace 会在追踪输出中使用方法参数名称。如果没有 `-parameters`，追踪只会显示 `arg0`、`arg1` 等。

```kotlin
// build.gradle.kts
tasks.withType<JavaCompile> {
    options.compilerArgs.add("-parameters")
}
```

## 2. 添加依赖

先从最小依赖组合开始，再按需添加你需要的集成。

```kotlin
dependencies {
    // 最小依赖
    implementation("ai.narrativetrace:narrativetrace-core:0.5.0")
    implementation("ai.narrativetrace:narrativetrace-proxy:0.5.0")

    // 可选集成
    testImplementation("ai.narrativetrace:narrativetrace-junit5:0.5.0")
    testImplementation("ai.narrativetrace:narrativetrace-junit4:0.5.0")  // 适用于 JUnit 4
    testImplementation("ai.narrativetrace:narrativetrace-testng:0.5.0")  // 适用于 TestNG
    implementation("ai.narrativetrace:narrativetrace-spring:0.5.0")
    implementation("ai.narrativetrace:narrativetrace-slf4j:0.5.0")
    implementation("ai.narrativetrace:narrativetrace-diagrams:0.5.0")
    implementation("ai.narrativetrace:narrativetrace-clarity:0.5.0")
    implementation("ai.narrativetrace:narrativetrace-opentelemetry:0.5.0")
    implementation("ai.narrativetrace:narrativetrace-micrometer:0.5.0")
    implementation("ai.narrativetrace:narrativetrace-agent:0.5.0")
    implementation("ai.narrativetrace:narrativetrace-servlet:0.5.0")
    implementation("ai.narrativetrace:narrativetrace-spring-web:0.5.0")
    implementation("ai.narrativetrace:narrativetrace-micronaut:0.5.0")
    implementation("ai.narrativetrace:narrativetrace-micronaut-http:0.5.0")
}
```

## 3. 选择集成路径

### 选项 A：JDK 动态代理（适用于任何 Java 应用）

```java
var context = new ThreadLocalNarrativeContext();
var tracedOrderService = NarrativeTraceProxy.trace(orderService, OrderService.class, context);

tracedOrderService.placeOrder("C-1234", "SKU-KB", 2);
System.out.println(new IndentedTextRenderer().render(context.captureTrace()));
context.reset();
```

当你的服务基于接口时，使用这种方式。

### 选项 B：Spring 自动包装

```java
@Configuration
@EnableNarrativeTrace(basePackages = {"com.example.myapp"})
public class AppConfig {}
```

当你希望通过 Bean 后处理自动包装符合条件的 Bean 时，使用这种方式。

### 选项 B2：Micronaut 自动包装

```yaml
# src/main/resources/application.yml
narrativetrace:
  base-packages:
    - com.example.myapp
```

无需任何启用注解——`narrativetrace-micronaut` 模块会在 classpath 上被自动发现。类及其接口与所配置包匹配的所有 Bean 都会被包装进追踪代理中。

HTTP 过滤器的搭建与配置细节，请参阅 [Micronaut 集成指南](Micronaut集成指南.md)。

### 选项 C：JUnit 5 自动上下文 + 追踪输出

```java
@ExtendWith(NarrativeTraceExtension.class)
class OrderServiceTest {
    @Test
    void customerPlacesOrder(NarrativeContext context) {
        var orderService = NarrativeTraceProxy.trace(new DefaultOrderService(), OrderService.class, context);
        orderService.placeOrder("C-1234", "SKU-KB", 2);
    }
}
```

特性：
- 通过参数注入为每个测试提供 `NarrativeContext`
- 测试失败时自动将追踪打印到控制台
- 场景名称派生自测试方法名（`customerPlacesOrder` → "Customer places order"）
- 默认就会为每个测试写出 `.md`、`.json`、`.mmd` 文件,外加套件级的 `clarity-report.md`——设置 `narrativetrace.output=false` 可退出

### 选项 D：JUnit 4 自动上下文 + 追踪输出

```java
public class OrderServiceTest {
    @Rule
    public NarrativeTraceRule narrativeTrace = new NarrativeTraceRule();

    @Test
    public void customerPlacesOrder() {
        NarrativeContext context = narrativeTrace.context();
        var orderService = NarrativeTraceProxy.trace(new DefaultOrderService(), OrderService.class, context);
        orderService.placeOrder("C-1234", "SKU-KB", 2);
    }
}
```

特性：
- 通过 `narrativeTrace.context()` 为每个测试提供 `NarrativeContext`
- 测试失败时自动将追踪打印到控制台
- 场景名称派生自测试方法名（`customerPlacesOrder` → "Customer places order"）
- 默认就会为每个测试写出 `.md`、`.json`、`.mmd` 文件——设置 `-Dnarrativetrace.output=false` 可退出
- 添加带 `NarrativeTraceClassRule` 的 `@ClassRule`，即可获得套件级的 `clarity-report.md` 和控制台摘要

> **在终端中查看失败追踪:** 上面所说的“失败追踪打印到控制台”写入的是测试进程的标准输出,而 Gradle 会把它捕获进 XML/HTML 报告——普通终端什么都看不到。要在控制台中实时看到它,请在 `test` 任务上启用标准流日志:
>
> ```kotlin
> tasks.test {
>     testLogging.showStandardStreams = true
> }
> ```
>
> `build/narrativetrace/` 下的追踪文件无论如何都会写出;这只影响控制台显示的内容。

配置使用系统属性（JUnit 4 没有 `junit-platform.properties`）：
- `narrativetrace.output` —— `true`/`false`（默认：`true`）
- `narrativetrace.outputDir` —— 路径（默认：`build/narrativetrace`）
- `narrativetrace.format` —— `markdown`/`text`/`mermaid`/`plantuml`（默认：`markdown`）

### 选项 D2：TestNG 自动上下文 + 追踪输出

使用 Gradle 插件时，`narrativeTrace { testFramework.set("testng") }` 就是全部配置：它会在 `testImplementation` 上添加
`narrativetrace-testng`，把 `test` 任务切换为 `useTestNG()`，并传入 `narrativetrace.*` 系统属性；监听器自行挂接。
请像对待 JUnit 4 那样自己声明 `org.testng:testng`（若没有声明，该模块的 `api` 依赖会带来 TestNG 7.10.2）。不使用插件时：

在 `testImplementation` 上添加 `narrativetrace-testng`，其余什么都不用做：TestNG 的 service loader
会在每次运行时注册它的监听器（`NarrativeTraceListener`）——Gradle 的 `useTestNG()`、Maven
surefire、IDE 都是如此。在测试类上标注 `@Listeners(NarrativeTraceListener.class)` 也能显式注册；
两者同时存在时，每个测试仍只追踪一次。

```java
public class OrderServiceTest {
    private final OrderService orderService = NarrativeTraceProxy.trace(
        new DefaultOrderService(), OrderService.class, NarrativeTraceListener.context());

    @Test
    public void customerPlacesOrder() {
        orderService.placeOrder("C-1234", "SKU-KB", 2);
    }
}
```

会写出什么——与 JUnit 集成相同的文件：
- 每个测试方法一份追踪，位于 `build/narrativetrace/traces/<TestClass>/`：`.md`、`.json`、一张时序图和结构化的 `.nt`
- 失败的测试会打印其失败报告，并在标准错误输出上打印 `narrativetrace: trace of <Class.method> → <绝对路径>`
- 运行结束时：`manifest.json`、`INDEX.md`（失败的测试排在前面）、`clarity-report.md` 以及控制台页脚，页脚会重复失败测试的指针
- data provider 的一行、`invocationCount` 的一次重复或 `@Factory` 的一个实例，都是一次独立的调用，拥有自己的文件——`<method>-001.md`，标注为 `Class.method[#1]`
- 审批追踪（`narrativetrace.approval=true`）会把每个测试与其已提交的 `.approved.nt` 比较，与 JUnit 下相同

配置使用与 JUnit 4 相同的系统属性（`narrativetrace.output`、`narrativetrace.outputDir`、
`narrativetrace.format`、`narrativetrace.level`、`narrativetrace.approval`、`narrativetrace.approvedDir`）。

限制：
- 测试通过 `NarrativeTraceListener.context()` 获取上下文——TestNG 无法把它作为测试方法参数注入
- 运行的文件在 TestNG 执行结束时写出；TestNG 没有按类结束的钩子，因此不会按类写出任何内容
- 整个测试 JVM 共用一条 pipeline；每个测试只看到它运行期间在自己线程上发生的调用，`parallel="methods"` 也是如此
- 带 `timeOut` 的测试会在单独的 TestNG 线程上执行方法体，因此这些调用不会出现在它的追踪中
- data provider 的一行按编号标注，从不按参数标注：渲染从不执行你的对象的 `toString`
- 不收集术语表（`narrativetrace.glossary`）——这一步属于 JUnit 5 扩展

### 选项 E：Java Agent（无需动态代理接线）

```bash
java -javaagent:narrativetrace-agent.jar=packages=com.example.myapp.* -jar your-app.jar
```

当你希望对选定包前缀下的类进行字节码插桩时，使用这种方式。未提供 CLI 参数时，Agent 会回退到 classpath 上的 `narrativetrace.properties`。挂载在同时携带 `narrativetrace-junit5` 扩展或 `narrativetrace-junit4` 规则的测试 JVM 上时，Agent 的捕获会落入与代理追踪测试相同的按测试文件——被插桩的类中不需要代理，也不需要注解(参见[配置指南 §3](配置指南.md#3-纯-java--agent-配置narrativetraceproperties))。

Agent 参数格式：`packages=<pkg1>;<pkg2>;...`

包模式支持通配符：

| 模式 | 匹配范围 |
|---|---|
| `com.example.*` | `com.example` 及其子包下的所有类 |
| `com.example.**` | 与 `.*` 相同（两者都匹配所有子包） |
| `com.example` | 与 `com.example.*` 相同（裸前缀，带边界检查） |

多个包：

```bash
java -javaagent:narrativetrace-agent.jar=packages=com.example.app.*;com.example.shared.* -jar app.jar
```

包分隔符是分号（`;`），不是逗号。未知的键会被忽略；重复的键会被拒绝。

#### 叙述需要 SLF4J 提供方 —— 代理从不自带

`-standalone` 代理 jar 打包了它需要的一切，*唯独*不含日志后端。这是刻意为之：宿主的
日志栈属于你，若代理偷偷塞进第二个提供方，就会与你已有的那个冲突。

因此，classpath 上没有提供方的最小宿主会在启动时看到 SLF4J 说一次：

```text
SLF4J(W): No SLF4J providers were found.
SLF4J(W): Defaulting to no-operation (NOP) logger implementation
```

没有任何东西坏掉 —— 追踪照常捕获，`captureTrace()` 照常返回 —— 只是不会写入日志。
按你的需要，有两个一行的解决办法：

| 你想要 | 这样做 |
|---|---|
| 日志中出现叙述 | 把提供方放到 classpath 上（`logback-classic`、`slf4j-simple` 等），或在宿主没有可达 classpath 时传 `loggingJars=/路径/到/provider.jar` |
| 完全不要叙述 | 以 `loggerName=`（空值）挂载，或设置 `-Dnarrativetrace.narration=off` |

叙述关闭后，代理根本不会碰 SLF4J —— 它启动时是静默的。**没有 SLF4J 提供方时，
代理同样是静默的** —— 它照常捕获，但叙述进了 NOP 日志器。

#### 代理运行时看不到的类将不加插桩地加载

匹配包过滤器是必要的，但并不充分。插桩后的字节码按名字调用
`ai.narrativetrace.agent.AgentRuntime`，因此只有当定义该类的类加载器能够解析到这个
类型时，这个类才会被织入。有两类类做不到：

- **注入到 bootstrap 的类** —— 例如 mockito 的内联 mock maker，会把它的方法分派器
  注入 bootstrap 类加载器
- **隔离的加载器**，它们不向代理所在的加载器委派

这些类将不加插桩地加载，并且代理会按加载器各说一次：

```text
narrativetrace-agent: cannot instrument org/example/Injected (ai.narrativetrace.agent.AgentRuntime is not visible from the bootstrap class loader); classes from that loader load uninstrumented
```

按加载器说一次，绝不按类说一次 —— 一个高频加载器不该淹没你的错误流。同一个 JVM 中
的其他一切仍正常被追踪；如果你关心的类正属于未插桩的那些，就收窄 `packages=` 让过滤
器不再匹配它们，或者改用代理（proxy）路径追踪它们。

#### 生成器与编译器生成的类从不被插桩

某些位于已匹配包下的类从来都不是业务边界 —— 它们是生成器或编译器生成的
字节码，不是你编写的代码。这些类会被无条件排除，没有开关可以重新启用它们：

- JDK 动态代理（`$Proxy0`、`$Proxy17` 等）
- 名称带有生成器自身标记的类：`$$`（CGLIB 的
  `$$EnhancerByCGLIB$$`、Spring 的 `$$SpringCGLIB$$`、lambda 自身的隐藏类）、
  `$ByteBuddy$`（Byte Buddy 的默认命名）或 `$MockitoMock$`
  （Mockito 的内联 mock maker）
- 隐藏类，以其 JVM 分配的 `/0x…` 后缀识别
- 桥接方法或合成方法 —— 编译器生成的真实方法副本，或没人写过的访问器

这是静默的 —— 不会有 `stderr` 输出行 —— 因为这是预期中的结构性情形；归属
从不依赖某个厂商的包名，所以给依赖添加一个新的 mock 库或代理库，都无需任何
配置改动。

#### 排除包：`exclude=<pkg1>;<pkg2>`

库和框架内部的实现细节 —— 从不是你自己的业务边界，但是按包命名而非按形态
识别的 —— 会和 `packages=` 一起被排除：

```bash
java -javaagent:narrativetrace-agent.jar=packages=com.example.myapp.*,exclude=org.mockito -jar your-app.jar
```

`exclude=` 总是优先：一个同时匹配 `packages=` 与 `exclude=` 的类不会被插桩，
即便被排除的包位于某个已匹配包内部（`packages=com.example`、
`exclude=com.example.generated` —— `com.example.generated` 下的类不会被
插桩；`com.example` 下的其他一切仍会被插桩）。只要完全没有给出 `exclude=`
（以及属性回退路径上的 `narrativetrace.exclude`），就会套用这份内置默认
列表：

| 前缀 | 原因 |
|---|---|
| `org.mockito` | Mock 库自身的分派器与生成的 mock 子类 |
| `net.bytebuddy` | Mockito、Hibernate 与许多代理工具底层使用的代码生成器 |
| `org.junit` | 测试运行器自身的辅助类 |
| `org.testng` | 另一个主流 JVM 测试运行器的辅助类 |
| `net.sf.cglib` | 经典 CGLIB 自身的内部实现 |
| `org.springframework.cglib` | Spring 重新打包的 CGLIB |
| `org.aspectj` | 另一个织入器的运行时 |
| `datadog` | 另一个 APM Agent 的运行时 —— 与它共同部署时避免递归插桩 |
| `io.opentelemetry.javaagent` | 最可能与之共同部署的另一个 APM Agent |

这个键是否出现决定一切：不给出 `exclude=` 就会套用
这份默认列表；给出 `exclude=` —— 即便后面什么都不写 —— 都代表显式声明了
整份列表，替换掉默认列表（给出空值则完全关闭第二份排除列表）。如果想在
默认列表的基础上扩展而不是替换它，就把这九个前缀复制进你自己的 `exclude=`
取值，再把你要加的内容放在它们旁边。像 `packages=` 一样会识别分隔符
（`org.acme` 永远不会匹配到 `org.acmeExtra`）；重复的 `exclude=` 键会像
重复的 `packages=` 键一样被拒绝。一个匹配上且被排除的类，会按被排除的前缀
各报告一次，绝不会按类各报告一次：

```text
narrativetrace-agent: cannot instrument org/mockito/internal/Foo (excluded package org/mockito/); classes under that package load uninstrumented
```


## 4. 配置追踪输出

追踪输出默认就会写入 `build/narrativetrace`——没有什么需要开启。下面的
小节是用来更改格式或退出的。

### JUnit 5（推荐）：`junit-platform.properties`

添加 `src/test/resources/junit-platform.properties`：

```properties
narrativetrace.format=markdown
```

要彻底退出，在同一个文件里设置 `narrativetrace.output=false`。两种情况都
无需任何 Gradle 接线。该文件仅用于测试，绝不会影响生产环境。

### Gradle：`gradle.properties`（备选）

在一处集中定义追踪输出设置：

```properties
# gradle.properties
narrativetrace.format=markdown
```

然后在 `build.gradle.kts` 中将其转发给测试 JVM：

```kotlin
tasks.withType<Test> {
    useJUnitPlatform()
    listOf("narrativetrace.output", "narrativetrace.outputDir", "narrativetrace.format")
        .forEach { key ->
            (findProperty(key) as? String)?.let { systemProperty(key, it) }
        }
}
```

### CLI 覆盖

系统属性会覆盖所有其他来源：

```bash
./gradlew test -Dnarrativetrace.output=false
./gradlew test -Pnarrativetrace.format=text
```

### 纯 Java / Agent：`narrativetrace.properties`

在 classpath 上添加一个文件（例如 `src/main/resources/narrativetrace.properties`）：

```properties
narrativetrace.packages=com.example.app.*;com.example.shared.*
```

## 5. 验证安装

运行测试：

```bash
./gradlew test
```

追踪文件会自动写出，除非 `junit-platform.properties` 中设置了 `narrativetrace.output=false`。

预期的输出结构：

```text
build/narrativetrace/
├── traces/
│   └── OrderServiceTest/
│       ├── customer_places_order.md
│       ├── customer_places_order.json
│       └── ...
├── diagrams/
│   └── OrderServiceTest/
│       ├── customer_places_order.mmd
│       └── ...
└── clarity-report.md
```

### 生成输出中包含的内容

当追踪带有 Span 上下文时，生成的文件会同时包含原始追踪 ID，
以及由它派生的确定性、人类可读的追踪名称。

Markdown frontmatter 包含：

```yaml
trace_id: 4bf92f3577b34da6a3ce929d0e0e4736
trace_name: bold elk soars
```

JSON 导出包含：

```json
{
  "trace": {
    "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
    "traceName": "bold elk soars"
  }
}
```

十六进制的 `traceId` 仍是权威标识符。`traceName` 是一个可读的别名，
便于在日志、仪表盘和团队讨论中使用。
