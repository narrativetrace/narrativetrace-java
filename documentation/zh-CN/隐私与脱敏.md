# 隐私与脱敏

[English](../privacy-and-redaction.md) | [Español](../es/privacidad-y-ocultacion.md) | [Português](../pt-BR/privacidade-e-ocultacao.md) | **简体中文**

这个库运行在你的进程内部,写出的文件会被你的团队共享——CI 产物、已提交的
基线、生产日志行。这一页是这份契约逐行展开的版本:哪里会脱敏、哪里不会脱
敏,以及 NarrativeTrace 保证什么、又完全不对什么做出承诺。

**测试期的追踪输出默认就会写入**——JUnit 5 扩展和 JUnit 4 集成会把每个
测试的 `.md`/`.json`/`.mmd` 产物写到临时目录 `build/narrativetrace`
(已被 git 忽略,每次运行都会重新生成),不需要任何配置;设置
`narrativetrace.output=false` 可以退出。这个默认值不会改变脱敏的内容或方
式——无论输出是默认开启还是显式开启,每个产物都要经过下面所述的同一个
`ValueRenderer` 和同一份拒绝清单。每个属性详见[配置指南](配置指南.md),
为什么这些都不该纳入版本控制见[应提交的内容](应提交的内容.md)。

## 脱敏,逐个界面来看

| 界面 | 能关闭内置脱敏吗? |
|---|---|
| 标准 JUnit 输出(proxy、agent、Spring、Micronaut、servlet、SLF4J) | 不能 |
| Agent 叙述 | 不能 |
| 你自己代码构造的自定义 `ValueRenderer` | 能——只能通过在构造函数里显式传入 `RedactionPolicy.DISABLED` |
| `@NotTraced` | 不适用——它本身就是执行脱敏的那一方,并且永远优先 |
| 结构化 `.nt` | 不适用——它一开始就不携带任何可供脱敏的值 |

以下结论对照代码验证过,不是从文档里推断出来的:每一个随包发布的集
成——`NarrativeTraceProxy` 与 `AgentRuntime`(真正发生捕获的那两处),以及
构建在它们之上的每一个框架模块——都以同样的方式构造自己的 `ValueRenderer`:
一个没有任何注入点的 `private static final` 字段:

```java
private static final ValueRenderer VALUE_RENDERER = new ValueRenderer();
```

`new ValueRenderer()` 默认使用 `RedactionPolicy.DEFAULT`。没有任何配置开
关、系统属性或插件 DSL 选项能够到达 `RedactionPolicy.DISABLED` 这个常
量——得到它的唯一办法,是应用代码自己直接构造一个 `ValueRenderer` 实
例,绕开每一条随包发布的集成路径。这是你自己源码里一个刻意的、可审查的
行为,而不是部署时可能被悄悄翻转的配置状态。

## 拒绝列表会捕获什么,以及什么能压过它

每一个通过反射渲染的值,都会受到两种彼此独立的脱敏机制作用:

1. **`@NotTraced`** 标注在参数、字段或记录组件上——无条件、在任何地方,
   永远脱敏。
2. **基于名称的拒绝列表**(`RedactionPolicy.DEFAULT`)——把**参数名、字段
   名和记录组件名**对照一份内置的多语言集合(`password`、`token`、`cvv`、
   `ssn`、`secret`、`authorization`、`cardNumber`,以及它们对应的西班
   牙语、葡萄牙语、法语、德语与中文写法等)进行匹配,再加上对值本身*形
   状*的第二重独立检查(是不是 JWT、是不是符合 Luhn 校验的卡号、是不是
   一个 `Set-Cookie` 字符串、是不是一个能通过自身校验位的国家身份证号、
   是不是一个带连字符的美国社会安全号),这样一个用未识别名称传入的持
   有者令牌依然会被捕获。

   参数名是在 2026-09-10 加入的。在此之前,这条轴只覆盖字段和记录组
   件,所以一个接收 `String password` 的方法会把它完整打印出来,除非
   该参数标注了 `@NotTraced`——而 README 说的却恰恰相反。这个判定现在
   发生在**捕获时**,用的是 proxy 和 agent 早已缓存的按方法元数据,这
   带来两个值得知道的后果:每次被追踪的调用,查找都不花任何代价;而且
   一个被拒绝的值根本不会进入 `TraceEvent`,因此它到不了审计路径、缓冲
   消费者,也到不了通过 pipeline SPI 挂上的监听器。它不是先渲染出来再
   被替换掉——一个格式化之后又被丢弃的密文,依然作为字符串存在过。

### 只要类型拥有状态,它自身的 `toString()` 就永远不被信任

这是本页其余内容所依赖的不变式,值得明确说出来:

> **一个声明了实例字段的类或 record,都会被逐字段地遍历,在任意深度都是
> 如此,并按字段查询这两种脱敏机制——无论其自身的 `toString()` 原本会打
> 印出什么。**

恰好有两类值会保留自己的文本。一类是**完全没有实例字段**的类:没有可
隐藏的东西,也没有可遍历的东西。另一类是**平台自身定义**的类——
`LocalDate`、`Duration`、`UUID`、`URI` 及同类——它们的 `toString()` 是
JDK 自身的格式而不是应用代码,而且它们本来就不可能声明你的某个字段。你
自己的代码声明的类,无论它继承自什么,都是应用代码。

唯一可以显式选用、回到精心编写渲染的方式是 **`@NarrativeSummary`**:一
个你*为了*这份追踪而编写的零参数方法,因此它的输出由你选择。即便如
此,它也不会被逐字信任——它的文本要经过值形态检查、控制字符转义和长度
上限,与一个 `String` 参数完全一样,因此一个插入了持有者令牌的摘要依然
会渲染为 `[REDACTED]`。

在 2026-09-11 之前,规则的方向恰好相反:除非类声明了 `@NotTraced` 字
段,否则任何 `toString()` 都会优先于内省。那项检查既不查询基于名称的拒
绝列表,也不查询字段的类型,这就留下了两条可乘之隙。一个简单的
`Login { username, password }`,只要写了手工的 `toString()`,就会在**深
度为零**处直接打印出密码——没有嵌套、没有包装器,也没有任何注解参与。
而任何外层类精心编写的 `toString()`,都会把嵌套的 `@NotTraced` 值原样通
过普通的 Java 字符串化打印出来,因为外层类本身没有声明任何敏感内容。改
为遍历字段,也把深度上限和循环检测重新放回了每个值的前面:你的
`toString()` 过去是在这两者之外运行的。

**这一代价是真实存在的,而它被接受了。** 一个 `toString()` 写得赏心悦
目、又没有 `@NarrativeSummary` 的值类,现在会被渲染成字段转储——
`Amount{currency: "EUR", units: 10}`,而不是 `EUR 10.00`。更丑,但正
确。请为那些渲染结果值得关注的类型添加 `@NarrativeSummary`。

**参数**的判定发生得更早,原因就在于判定的时机不同。一个名字被拒绝列
表拒绝的参数,会在捕获时就被判定,早于这个参数被传给任何渲染器之前——
所以这个值上什么都不会被调用。这不是不一致:字段名是*通过*内省被发现
的,而参数名在值被触碰之前,就已经能从方法签名里知道了。

脱敏能穿透**任意深度的任何包装器**——`Optional`、`Future`、
`AtomicReference`、`AtomicReferenceArray` 以及独立的 `Map.Entry` 都会被
打开,而不是通过它们自己的 `toString()` 渲染,它们所持有的内容会按同样
的规则渲染,而这条规则又会对其中的内容再次生效。`Map` 的**键**也会按
同样的方式被遍历,因此一个复合键无法借由这个最难避免字符串化的地方把
字段带出来。而且脱敏**优先于点名它的叙述模板**:`@Narrated`/`@OnError`
里的 `{param.property}` 在解析到一个被脱敏的成员时,不管路径多深,始终
解析为 `[REDACTED]`,绝不是字面值。

### 当渲染某一部分失败时

一个 `toString()`、`@NarrativeSummary`、getter 或访问器抛出异常的值,
代价只限于它自己所在的那个位置:那一部分会渲染为
`<error: IllegalStateException>`——**只有异常的类型名称,别无其他**——
值的其余部分会完整渲染。异常消息被刻意排除在外。异常消息常常会把那个
格式化失败的值本身也带出来(`"cannot render " + password`),因此如果
标记里带上了它,就会把渲染器自身的失败路径变成一条泄露通道。

完整细节与实例见[注解指南](注解指南.md)。

## 保证

- **追踪失败与宿主执行是隔离的。** 每一条记录路径都做了异常隔离;两个流
  水线消费者都会吞掉自己的错误。一个会抛异常的 `toString()`、一个已满的
  缓冲区,或一个损坏的 appender,都不会改变你的方法返回什么或抛出什么。
- **标准输出遵守脱敏规则。** 见上面的表格——没有任何一条随包发布的集成
  提供绕过它的办法。
- **结构化 `.nt` 产物完全不携带运行时的值。** 只有名称、调用层级与结果种
  类——没有任何提示注入面,而且这是一条属性测试(ADR-002)保证的性质,不
  是某个人可能忘记执行的策略。
- **带缓冲的分析路径可能会丢弃事件,但它总会报告丢失。** 它绝不会阻塞调
  用方,也绝不会超出自己的容量上限;一次丢过事件的捕获,会在自己的footer
  里打印丢失数量,而不是悄悄地少报。

## 不做的承诺

- **没有"零开销"这种说法。** 追踪确实做了工作,而工作是有代价的——具体
  数字见 [README 的性能小节](../../自述文件.md#性能)。
- **不追踪私有方法。** 两条捕获路径都只能看到接口方法(proxy)或非私有方
  法(agent);一个私有方法的分支,只能从追踪里出现的、*它*所发起的那些调
  用推断出来。
- **在任何基于代理的路径上,都不会自动追踪没有接口的 Bean。**
  Proxy、Spring 与 Micronaut 全都通过 JDK 动态代理来包装,一个没有接口的
  类会被原样保留——静默地保留,而不是报错。Java Agent 是唯一没有这个限
  制的路径。
- **目前还没有 Agent 排除列表。** `AgentConfig` 只解析
  `packages`、`loggerName`、`level` 与 `loggingJars`——只能包含,没有办法
  从一个已包含的包里再挖出一个例外。
- **今天还不支持 Android 或 GraalVM 原生镜像。** 完整细节,包括*为什么*
  Android 是"不支持"而不是"暂时还没到",见
  [安装指南 § 兼容性](安装指南.md#兼容性)。

## 生产环境的丢失模型,图示

每个事件都会同步写入持久的日志流,*同时*还会发布到一个尽力而为、容量有
界的内存缓冲区——双路径流水线的两个半边在设计上承担相反的义务:

```text
同步日志路径(SLF4J,在调用方线程上内联执行)
   绝不能让宿主应用失败
   绝不能被分析路径的失败拖累而饿死
   持久——这就是记录本身

带缓冲的分析路径(有界环形缓冲区,排空进入保留的存储)
   可能在负载下丢弃事件,并且总会说明这一点
   绝不能阻塞调用方
   绝不能超出自己的容量上限(默认 65,536 个槽位)
   尽力而为——这是分析,不是审计
```

丢失缓冲区,丢失的是这次运行的分析保真度。丢失日志流,丢失的是记录本
身。正是这种不对称,让它们成为两条有着两种不同失败行为的路径,而不是一
条带单一权衡的路径。

## 这一页没有涵盖的内容

NarrativeTrace 在你的流水线各个阶段——开发、CI/验收、生产——分别处在什
么位置,见[生命周期指南](生命周期指南.md)。它与 AOP 代理、契约库,或另一
个包装了相同类的 agent 叠加时会发生什么——嵌套顺序会改变追踪*读起来*的样
子,但绝不会改变方法*返回或抛出*的内容,因为记录绝不会替换结果——见
[选择集成方式 § 与其他包装器叠加](选择集成方式.md#与其他包装器叠加)。
