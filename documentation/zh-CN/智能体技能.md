# 智能体技能

NarrativeTrace 提供**技能**(skills):可供智能体加载的流程,它们运行经过测试的命令,并把
完成的条件设在一个 `verify` 步骤上,而不是一份智能体可能读也可能不读的文档。技能被刻意设计得
很薄——检查、诊断或生成的逻辑都放在经过测试的库代码里;技能本身的工作只是知道何时该出手、调用
那些经过测试的代码、并在上下文中解读结果。

## 四个技能:配置、诊断、清晰度与问题反馈

- **`add-narrative-tracing`** ——把 NarrativeTrace 安装进一个项目,并让它产出第一条追踪:用真实
  的工具链安装、用 `NarrativeTraceProxy.trace` 包装一个类、渲染并运行第一条追踪,然后接入一个真
  实的日志记录器(`narrativetrace-slf4j` 加 Logback)。它会运行 `narrativetrace-doctor` 并把接力
  棒交给它——这是两个技能之间的接缝——最后以预览 `narrativetraceInit` 收尾,让下一次会话一开始
  就能找到这些技能。它只预览、绝不应用:一个擅自往 `AGENTS.md` 里写东西的技能,正是安装器要避
  免的那种后置安装钩子。
- **`narrativetrace-doctor`** ——只做诊断,而且是**只读**的:它绝不编辑、生成或删除任何文件。运
  行经过测试的 CLI、读取它的报告,并走完普通 CLI 输出本身覆盖不到的部分:在测试里证明脱敏确实生
  效、在对渲染出的追踪做断言之前先读一遍它,以及审批追踪流程(标记为尚未研究——它自己的评测单元
  仍待完成)。它读到的每一条结论还会指名修复这一类问题的技能(JSON 报告里的 `skill`,文本形式
  里修复建议下方的 `skill:`),因此拿到报告的智能体知道接下来该照着这几套流程中的哪一套走;没有
  任何技能能修复的结论会以 `null` 明说这一点。
- **`add-narrativetrace-clarity`** ——运行首次静态命名扫描,检查新生成的扫描产物,解释按影响
  排序的问题及逐元素说明,并且仅在用户要求时添加明确的清晰度门禁。
- **`narrativetrace-feedback`** ——反馈 NarrativeTrace 自身的缺陷:doctor 的某条检查判断有误、
  它给出的修复不起作用、某个技能步骤无法照做、安装提示词的措辞把人引到了错误的地方,或者在一
  个配置正确的项目上库本身表现异常。它背后那个经过测试的动词会从项目里起草报告(安装坐标、
  doctor 自己的 JSON 报告,以及最多一份结构化追踪),并且**拒绝写出任何携带你追踪中的值的报
  告**——同时指名是哪条规则拒绝了它,这样你有一处具体可改的地方,而不是一句可以忽略的警告。随
  后技能会把整份草稿展示出来,并且只问一次是否公开提交。它不会把任何东西发往任何地方,也不会
  在没有用户在独立一轮里给出答复之前提交任何东西。

两者相辅相成:一个全新的项目从 `add-narrative-tracing` 开始;一个已经装好 NarrativeTrace、但哪里
不对劲的项目从 `narrativetrace-doctor` 开始。两条路径最终都会走到 doctor——从那时起,诊断就归它
管了。`add-narrativetrace-clarity` 负责首次静态命名报告和可选的清晰度门禁;它不安装追踪,
也不采集术语表。当问题最终属于我们而不是项目本身时,路径就终于 `narrativetrace-feedback`——
doctor 自己的收尾规则就指向它。

## 安装它们

在你想安装它们的项目里,一条命令就够:

```bash
./gradlew narrativetraceInit --diff
```

这会**预览**安装,什么都不写。它会报告这份计划——加上 `--json`,同一份计划就是脚本可以据以判断
的信封:

```json
{
  "carrier": "ai.narrativetrace:narrativetrace-cli:0.2.5",
  "actions": [
    {"kind": "create", "path": ".agents/skills/narrativetrace-doctor/SKILL.md", "status": "planned"},
    {"kind": "create", "path": ".agents/skills/add-narrative-tracing/SKILL.md", "status": "planned"},
    {"kind": "create", "path": ".agents/skills/add-narrativetrace-clarity/SKILL.md", "status": "planned"},
    {"kind": "create", "path": ".agents/skills/narrativetrace-feedback/SKILL.md", "status": "planned"},
    {"kind": "create", "path": "AGENTS.md", "status": "planned"}
  ],
  "exitCode": 0
}
```

读完之后,再去掉这个参数跑同一条命令就会应用它。在你这样做之前什么都不会被写入;既没有后置安装
钩子,也没有哪个构建步骤会背着你安装技能。它会写入:

- 每个目录内技能的 `.agents/skills/<名称>/SKILL.md` ——始终如此,不论你用哪个智能体。
- 当项目里有 `.claude/` 目录或 `CLAUDE.md` 时(或者用 `--vendor claude`;`--vendor none` 可以关
  掉),额外写入 `.claude/skills/<名称>/SKILL.md`。
- `AGENTS.md` 里一段带标记的小节:文件不存在时创建,上一次运行写过时就在它自己的标记之间替换。
  一个已经存在、但没有我们标记的 `AGENTS.md` 需要 `--write-existing`,这样首次运行绝不会往你没
  料到它会碰的文件里追加内容。
- 在已有的 `CLAUDE.md` 里写一行 `@AGENTS.md` 导入语句,并且绝不自己新建 `CLAUDE.md`。

重复运行是安全的:凡是写入结果与现状相同的动作都会被丢弃,所以一个已经最新的项目什么都不会计划。
`./gradlew narrativetraceUninstall` 只移除当初安装的东西——只有带着安装器自己印记的页面才会被删,
只有安装器创建、且里面没剩下任何属于你的内容的文件才会被删。完整的任务与参数参考见
[Gradle 插件指南](Gradle插件指南.md#narrativetraceinit)。

没有 Gradle 插件时,同一个安装器就是启动器上的一个动词:`narrativetrace init --dry-run` 预览,
`narrativetrace init` 应用(CLI 保留 `--dry-run`,那里没有东西会把它遮住;Gradle 任务不能用这个
名字,因为 Gradle 自带的 `--dry-run` 会跳过任务图里的每一个任务)。通过插件运行时,上面那份计划
里的载体会是 `ai.narrativetrace:narrativetrace-skills` 而不是启动器——同样的页面,只是来自项目
已经取到的那个归档。

### 手工安装,备用路径

复制同样可行,而且对于没有自己构建系统的智能体来说,这是唯一的路径:

- **Claude Code**:渲染出的 `SKILL.md` 文件就放在本仓库的
  [`.claude/skills/narrativetrace-doctor/`](../../.claude/skills/narrativetrace-doctor/SKILL.md)
  和
  [`.claude/skills/add-narrative-tracing/`](../../.claude/skills/add-narrative-tracing/SKILL.md)
  和 [`.claude/skills/add-narrativetrace-clarity/`](../../.claude/skills/add-narrativetrace-clarity/SKILL.md)
  里。将所需目录复制到你自己项目的 `.claude/skills/<名称>/` 下,Claude 就会自动识别,
  并可直接通过技能名称调用。
- **Codex**:同一份目录也会渲染出
  [`.agents/skills/narrativetrace-doctor/`](../../.agents/skills/narrativetrace-doctor/SKILL.md)
  和
  [`.agents/skills/add-narrative-tracing/`](../../.agents/skills/add-narrative-tracing/SKILL.md)
  和 [`.agents/skills/add-narrativetrace-clarity/`](../../.agents/skills/add-narrativetrace-clarity/SKILL.md)
  ——这是 Codex CLI 为项目自身技能所记录的布局。它的 frontmatter 只带 `name` 和
  `description`(Codex 没有记录 `when_to_use` 或 `allowed-tools` 这两个键);页面正文完全相同。
  把所需目录复制到你自己项目的 `.agents/skills/<名称>/` 下,Codex 就会用同样的方
  式识别它。
- **任意智能体、任意平台**:任何会读取 `AGENTS.md` 的智能体都会看到本仓库自己的 `AGENTS.md` 在
  `<!-- narrativetrace:skills:start -->` 标记之间携带的这条常驻提示——四个技能各自的名称和描
  述——这样即使某个智能体从未想过要去找,它也知道这些技能的存在。
- **Gemini** 会按一种偶发的、受配额限制的节奏针对同一份目录运行(见
  [Tier B——LLM 试验](../../narrativetrace-skills-catalogue/evals/README.md)),而不是每次提交都跑;它目前
  还没有自己渲染出的布局——今天,复制上面 Claude 或 Codex 的文件是最接近的路径。

### doctor 会就此给出报告

它的其中一项检查 `config.skills-installed` 会读取每一份已安装的
`SKILL.md` 以及安装器留在其中的印记,并在技能缺失、其中某一项不见了、或者印记指向的发行版与项目
解析到的发行版不一致时判定失败——这样,过期的副本会作为一条结论显现出来,而不是让智能体悄悄照着
上一个发行版的说明行事。位于某个技能路径上、却没有该印记的目录,会被报告为属于别人,并且永远不
计为已安装。当根本无法解析到载体时——离线构建,或者没有任何仓库提供它——这项检查会说它无法判断
并通过:离线并不是缺陷。

## 来自某个注册中心

一个项目可以带着这些技能,而从来没有人在这里运行过安装器——这有三种状态:

1. **由 `init` 安装**——已提交,属于团队。这是 `config.skills-installed` 唯一会通过的状态:
   页面带着来源说明那一行,并且与这个项目解析到的版本一致。
2. **从某个注册中心个人安装**(Claude Code 的插件缓存)——只属于你自己。按设计对 doctor
   不可见:它诊断的是项目,而个人安装既到不了任何同事,也到不了任何别的智能体。
3. **注册中心安装进项目里**(`npx skills add`、`gemini skills install --scope
   workspace`)——这正是本仓库自己渲染出的页面,只是由注册中心而不是 `init` 放进去的,
   所以还没有带上来源说明那一行。

自己先试一下这些技能,不碰项目本身:

```text
/plugin marketplace add narrativetrace/narrativetrace-java
/plugin install narrativetrace-java@narrativetrace-java
```

然后运行 `./gradlew narrativetraceInit --diff`,读一遍这份 diff,再去掉这个参数运行一次,
让 `AGENTS.md` 指向它们。

从开放标准的注册中心把它们装进项目里:

```text
npx skills add narrativetrace/narrativetrace-java
```

然后运行 `./gradlew narrativetraceInit --diff`,读一遍这份 diff,再去掉这个参数运行一次,
让 `AGENTS.md` 指向它们。

注册中心留下的页面,绝不会仅仅因为它在那里就被拒绝。`init` 会把它——除了来源说明那一行——逐字
节与自己会渲染出的内容比较。一份与这个版本自己的页面完全相同的页面会被**采纳**——计划上写的
就是“采纳”而不是“替换”,因为读到它的人必须知道,没有任何人的东西被覆盖掉。这就是计划自己的
文字,照原样引用,从未在这里重打过:

```java
  private static final String ADOPTED =
      "adopted: identical to this carrier's page, so only the provenance line is added";
```

一份不一样的页面——另一个版本,或是被手工改过的——仍然保留 `--force` 要处理的那种普通拒绝。
`npx skills add` 还会把 `.claude/skills/<名称>` 变成指向开放标准页面的一个符号链接;`init`
绝不会透过这样的链接去写。一个链接,如果它指向的东西本来就会被采纳或者已经属于我们,就会被替换
成一个带着正确风味的真实目录;其余任何链接都会被拒绝,因为 `--force` 覆盖的是内容,从不覆盖
链接本身。

而这是 doctor 自己给出的修复建议,用同样的方式照原样引用——针对一个页面都在、却什么都没带上
的项目:

```java
  /** Both spellings of the same command: Gradle owns {@code --dry-run}, so the task says diff. */
  private static final String INIT_COMMANDS =
      "./gradlew narrativetraceInit --diff (or narrativetrace init --dry-run)";

  /** What a skill directory that is present but not ours is called in a message. */
  private static final String NOT_OURS = " (there, but not ours)";

  /**
   * What a page with no provenance line most often IS: a registry install (D5 state 3) — `npx
   * skills add`, or a workspace skills install — of this repository's own rendered pages. Naming
   * the case matters because the obvious reading of "not ours" is "somebody else's work", which
   * invites a `--force` nobody needs: `init` ADOPTS a page identical to this release's.
   */
  private static final String FROM_A_REGISTRY =
      " Pages that are there without our line usually came from a registry (npx skills add, a"
          + " plugin or workspace install). Run "
          + INIT_COMMANDS
          + ", read the diff, then run it without the flag — a page identical to this release's is"
          + " adopted, and no --force is needed.";
```

## 它们是如何构建的

任何技能都不应手工编辑。
`narrativetrace-skills-catalogue/src/main/java/ai/narrativetrace/skills/catalogue/` 包含四个唯一的来源;
它们的类型化步骤渲染出四个 Claude 页面、四个 Codex 页面、载体自己保存的两种风味副本连同它的
`catalogue.json` 索引——也就是已发布的 jar 交给 `narrativetraceInit` 的那份东西——本仓库
`AGENTS.md` 中的小节,以及让本仓库成为一个 Claude Code 插件市场的 `.claude-plugin/marketplace.json`
清单:漂移测试(`RenderDriftTest`,已接入 `./gradlew check`)会在这十九份产物中
的任何一份偏离类型化源头时让构建失败;另一个测试则会在载体里出现任何别的东西时让构建失败。一个技能渲染出的 `name:` 永远是它的规范名称,绝不是缩短过的“claude 片段”——本仓库
自带的 `.claude/skills/` 或 `.agents/skills/` 目录是一个没有插件前缀可以依附的扁平命名空间,所
以名称本身就必须在全局范围内可自我识别。另一个测试套件(`SkillReplayer`,Tier A2)会针对
相应的真实 fixture(包括独立的 Clarity 消费项目),机械地重放每个步骤中的每一条命令及机器可检查的
`verify`——就在今天,确定性地、不借助任何 LLM——它保持绿色,意味着这些说明此刻确实可以照着执行,
而不只是听起来说得通的文字。一条 A 级 lint 会把对私有规划笔记的引用、对本仓库 Pro 版兄弟项目的引
用、CI 配置文件名、以及 git 哈希都挡在渲染后的页面之外:说明理由的句子可以出现,但点出出处的引用不
行。还有第二条 lint 守着那个唯一“缺席才是功能”的 frontmatter 字段:步骤有可能把某些东西变成公开
内容的技能——今天是 `narrativetrace-feedback`——不得声明任何 `allowed-tools`,因为该字段会在加载
技能的那一轮里预先批准它列出的工具,而一个预先批准了自己提交命令的反馈技能,恰恰会让环境在最该
发问的地方不再发问。
