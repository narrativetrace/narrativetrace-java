# 应提交的内容

[English](../what-to-commit.md) | [Español](../es/que-commitear.md) | [Português](../pt-BR/o-que-commitar.md) | **简体中文**

NarrativeTrace 会写出两类文件:描述某一次运行的生成产物,以及描述一份预
期契约、经过审阅的基线。要提交的是第二类,不是第一类。

每一个测试期产物默认都会写到临时目录 `build/narrativetrace`——不需要任何
配置,设置 `narrativetrace.output=false` 可以退出(见[配置指南](配置指南.md))。
临时正是重点所在:它位于 `build/` 之下,因此完全不需要这页所说的那种自
律——它已经被排除在外、每次运行都会重新生成,并且可以随时删除。

| 产物 | 要提交吗? | 原因 |
|---|---|---|
| `build/narrativetrace/traces/*.md` | 不要 | 每次运行都会重新生成;通常是 CI 产物,不是源码 |
| `build/narrativetrace/traces/*.json` | 不要 | 同一条追踪的规范 JSON 版本——每次运行都会重新生成 |
| `build/narrativetrace/diagrams/*.mmd` | 不要 | 每次运行都会重新生成 |
| `build/narrativetrace/manifest.json` | 不要 | 每次运行都会重新生成;它顶层的 `run` 对象(`id`、`name`——运行自己的三词短语)命名的是*这一次运行*,而不是某个场景,所以即使其他一切都没变,它也会在每次运行时改变 |
| `build/narrativetrace/structural/*.nt` | 不要 | 控制台 delta 与失败报告用来比对的、最近一次绿色的*本地*基线——不是审批基线(见下文) |
| `build/narrativetrace/clarity-report.md` | 不要 | 生成的报告,不是一个决定——`clarityCheck` 读的是它旁边同样生成出来的 `clarity-results.json` |
| `src/test/narratives/<Class>/<scenario>.approved.nt` | **要** | 经过审阅的审批基线(只有开启了[审批模式](结构化追踪格式.md)才会存在)。这是列表里唯一一个属于刻意决定、而不是输出的文件 |
| `src/test/narratives/<Class>/<scenario>.received.nt` | 不要 | 在审批不匹配、或者还没有基线时写出。审阅它,运行 `./gradlew approveNarratives` 把它提升为基线,然后删除它,或者让任务自己清理——绝不要提交 received 文件本身 |
| `src/test/narratives/<Class>/<scenario>.incomplete.nt` | 不要 | 当运行本身不完整时(尽力而为丢失,或一次被拒绝的异步作用域),会写出这个而不是 `.received.nt`。`approveNarratives` 会按名字故意忽略它——见[结构化追踪格式](结构化追踪格式.md) |
| `glossary.json` / `glossary.md` | **要**,如果用了术语表采集 | 由 `glossaryScan` / `glossary.set(true)` 提交到仓库根目录;已提交的文件才是清晰度评分与词汇检查实际读取的内容。"一份文件,一套评审流程" |
| `.claude/skills/**/SKILL.md`、`.agents/skills/**/SKILL.md`、`AGENTS.md` 里的 `<!-- narrativetrace:skills:* -->` 小节 | **要** | `narrativetrace-skills-catalogue` 类型化目录的构建产物,不是测试运行产物——提交方式和 `glossary.json` 一样:重新生成、在 diff 里评审、并针对漂移做检查(`RenderDriftTest`,已接入 `./gradlew check`),而不是手工编辑 |
| `skills-lock.json` | **要**,如果你的团队用了 `npx skills add` | 由 `npx skills add` 写在项目根目录——这是该注册中心自己记录的安装内容与来源;提交它,就像提交团队依赖的任何其他依赖锁定文件一样 |
| `.claude-plugin/marketplace.json` | **要** | 本仓库自己的清单(第 4 阶段):与上面那一行同一份类型化目录的构建产物,经过渲染并针对同一个漂移测试做检查——绝不手工编辑 |

在执行过 [`narrativetraceInit`](Gradle插件指南.md#narrativetraceinit) 的项目里,要提交的仍然是
同样这三个路径,而每一份已安装的 `SKILL.md` 都带着一行来源说明,写明它是从哪个版本安装的——正是这
个印记让 `narrativetraceUninstall` 知道某个页面属于我们,也让 doctor 能区分一份最新的安装和一份过
时的安装,所以一份没有它的页面提交上去,就成了谁都无法安全移除或刷新的页面。使用者提交的
`AGENTS.md` 小节位于 `<!-- narrativetrace:start ... -->` 与 `<!-- narrativetrace:end -->` 之间:你
写在这两个标记之外的内容属于你,并且能在每次重新运行后存活下来;而写在它们之间的内容会被替换。

个人的插件安装(Claude Code 的 `/plugin install narrativetrace-java@narrativetrace-java`)完全不
会往项目里写任何东西——它活在你自己的插件缓存里,所以没有什么需要为它提交的内容。

`build/` 下的一切已经被随包发布的 `.gitignore` 覆盖了(`build/` 就是第一
行)。`src/test/narratives/` 没有被覆盖——那里的 `.approved.nt` 文件是要被
跟踪的,但躺在它旁边的 `.received.nt` 不会被自动排除。如果你的团队在提交
前不习惯删除已经审阅过的 `.received.nt`,就为它加一条显式的忽略规则:

```gitignore
src/test/narratives/**/*.received.nt
src/test/narratives/**/*.incomplete.nt
```

## 一句话说清这条规则

如果一个文件的存在只是因为跑了一次测试,它就是输出——不要提交它。如果一
个文件的存在是因为有人审阅并接受了它,它就是一份基线——提交它,并且预期
它的 diff 会像快照测试的 diff 一样被拿到代码评审里阅读。

## 审批基线在结构上就是无值的

一份 `.approved.nt` 文件永远不包含参数或返回值(ADR-002)——只有调用结
构、名称与结果种类。这正是它能被安全提交、并且在多次运行之间保持稳定的
原因:返回值变了但结构没变,永远不会触碰到基线;评审一份 diff,也永远不
意味着要在合并请求里读到运行时数据。NarrativeTrace 在一个你的团队会共享
的文件里到底放什么、不放什么,其余部分见[隐私与脱敏](隐私与脱敏.md)。

## 审批模式,从头到尾

```text
测试通过
   |
   v
把当前结构与已审批基线比对
   |
   +-- 相同   --> 通过,什么都不写
   +-- 不同   --> 写出 .received.nt 并失败
                  |
                  v
              人来审阅这份 diff
                  |
                  v
           ./gradlew approveNarratives
                  |
                  v
           .approved.nt 更新,提交它
```

这个失败状态是刻意设计的:一个通过了、但*形状*变了的测试——包括一次 AI
agent 在原本正确的重构里悄悄带入的变化——必须被人看一眼并明确批准,而不
是仅仅编译通过就算数。没有什么会被静默接受,也没有什么会被静默丢
失:一次不完整的运行会改写 `.incomplete.nt`,并且是按子序列包含关系比
对、而不是按相等比对,所以一次短运行永远不可能变成已提交的基线。
