# 修改复杂流程前先审查它

[English](../../recipes/review-a-complex-flow-before-changing-it.md) | [Español](../../es/recetas/revisa-un-flujo-complejo-antes-de-cambiarlo.md) | [Português](../../pt-BR/receitas/revise-um-fluxo-complexo-antes-de-altera-lo.md) | **简体中文**

## 问题

> 在你动结算之前，先告诉我它实际上做了什么。

读源码回答的是它*能*做什么。一次运行回答的是它拿着这些输入*实际*做了什么——顺序如何、用的是
哪些值，以及流程在哪里离开了你马上要改的那段代码。这一页故意从不展示实现：读一次运行而不是读
源码，意义就在这里。

## 最小准备

那两份追踪产物除了[安装](../安装指南.md)什么都不需要。日志行需要 SLF4J 模块和一份 Logback
配置，和[给这个服务加日志](给这个服务加日志.md)里完全一样。捕获级别是一个属性，而
`SUMMARY` 就是这一页与默认的 `DETAIL` 并排使用的那个：

```kotlin
// build.gradle.kts
narrativeTrace {
    tracingLevel.set("SUMMARY")   // "OFF" | "ERRORS" | "SUMMARY" | "NARRATIVE" | "DETAIL"
}
```

## 场景

这个流程的一次有代表性的运行——现成的测试是最省事的那个借用对象，而这就是那个测试：

```java
// src/test/java/com/example/checkout/CheckoutReviewFixture.java
package com.example.checkout;

import static org.assertj.core.api.Assertions.assertThat;

import ai.narrativetrace.api.event.Traceparent;
import ai.narrativetrace.core.context.NarrativeContext;
import ai.narrativetrace.junit5.NarrativeTraceExtension;
import ai.narrativetrace.proxy.NarrativeTraceProxy;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;

/**
 * One successful checkout, the flow
 * documentation/recipes/review-a-complex-flow-before-changing-it.md is read before changing
 * anything.
 *
 * <p>A fixture because two readers need the same run under different settings: {@code
 * ReviewFlowRecipeTest} runs it through the JUnit Platform launcher once at DETAIL and once at
 * SUMMARY, and the Gradle task {@code recipeReviewFlowLog} runs it alone so one scenario's log
 * lines land in one file. It passes either way — nothing here fails by design.
 */
@ExtendWith(NarrativeTraceExtension.class)
class CheckoutReviewFixture {

  /** A fixed W3C traceparent, so the page's embedded artifacts name the same trace every run. */
  static final String DEMO_TRACEPARENT = "00-c4e1d0a7c4e1d0a7c4e1d0a7c4e1d0a7-c4e1d0a7c4e1d0a7-01";

  @Test
  void a_customer_buys_two_keyboards(NarrativeContext context) {
    context.adoptTraceparent(Traceparent.parse(DEMO_TRACEPARENT));

    var stock = new InMemoryInventory("SKU-KB", 5);
    var repository = new InMemoryOrderRepository();

    var inventory = NarrativeTraceProxy.trace(stock, InventoryService.class, context);
    var payments =
        NarrativeTraceProxy.trace(new CardPaymentService(), PaymentService.class, context);
    var orders = NarrativeTraceProxy.trace(repository, OrderRepository.class, context);
    var checkout =
        NarrativeTraceProxy.trace(
            new DefaultOrderService(inventory, payments, orders), OrderService.class, context);

    var orderId = checkout.placeOrder("C-1234", "SKU-KB", 2, "4242424242424242");

    assertThat(orderId).isEqualTo("ORD-C-1234-SKU-KB-2");
    assertThat(stock.availableUnits("SKU-KB")).isEqualTo(3);
    assertThat(repository.saved()).hasSize(1);
  }
}
```

## 怎么读

**流程，从 `DETAIL` 产物看。** `#1` 是测试发起的那次调用，也是唯一的根：缩进在它下面的一切都
发生在它内部，顺序就是打印出来的顺序。`#1.1` 在扣任何款之前先预留了两件；`#1.2` 扣了 7998——
两件货每件 3999，所以价格是从数量推出来的，而不是传进来的；`#1.3` 保存的订单已经带着 `#1`
返回的那个编号。当成一句话读：这次结算先预留、再扣款、最后保存，而订单编号在保存之前就已经
铸好了。一个先扣款后预留、或者先保存后扣款的改动，改的就是*这件事*，而现在你知道这一点，不必
相信某条注释。

**每个级别各有什么用。** `DETAIL` 带着参数值，是你在改这个流程时要读的那个。在 `SUMMARY` 下
每个参数值都是 `…`——在捕获时就被压掉了，而不是渲染时藏起来——而且只保留根和叶子调用；这个流程
深两层，所以没有哪个栈帧是中间层，于是出现的仍是同样四次调用。更深的流程会丢掉中间部分。返回值
在每个激活的级别上都保留：返回值是一段叙事的有效载荷。当你需要的是形状和结果、而值只是成本时
就用 `SUMMARY`——CI 的一次运行、一次长时间的压测——在生产上则先用 `OFF`/`ERRORS`，直到你需要
更多。

**哪一份输出给人读，哪一份给智能体读。** 日志行是给值班的人看的：它们和服务记录的其他一切交织
在一起、带着那些值，并以追踪的名字为索引——`[solid wand romps]`——所以一次结算能从一个嘈杂的
文件里 grep 出来。`.nt` 是给智能体和评审者看的：**在结构上就是无值的**——把它和上面那行日志比
一比，差别不是值被替换掉了，而是它们从来没被写出来过。
`(customerId, sku, quantity, cardNumber)` 是参数的*名字*；`→ value` 说明返回了一个值，但不说
是哪个。正是这一点让它可以被提交、可以在评审里看差异、也可以交给一个模型：它不可能泄露某个客户
的编号，而且数据变了它也不变——只有*调用*变了它才变。把它钉住，就是
[审查重构：行为变了吗](审查重构行为变了吗.md)。

## 没有被捕获的部分

- **未包装类内部的调用。** 这里包装了四个接口；它们背后两个类之间的调用，或者一个私有方法，
  永远不会出现。看起来很浅的流程可能其实很深。
- **所选集成拦不到的东西。** JDK 代理只看到*经由*被包装引用发出的调用：一个类对自己发起的内部
  调用（`this.helper()`）对它是不可见的，而 Java agent 会看到。
  [选择集成方式](../选择集成方式.md)讲的是每条路径的取舍，而这正是其中改变你在这里能读到什么
  的那部分。
- **离开了线程的工作。** 交给 executor 而没有带上上下文的调用不会再往前走；追踪就在线程结束的
  地方结束。
- **被拒绝名单或值形状规则抓住的值**，这里是 `cardNumber` 和 `card`，在日志和 `DETAIL` 产物里
  都是 `[REDACTED]`，而在 `.nt` 里按构造就不存在。
- **一次运行，不是契约。** 换一个输入就走另一条路——缺货的 sku 根本到不了 `#1.2`。

**对应的技能：** `narrativetrace-verify`——它先把意图写下来，跑最小的真实路径，并在把任何事情
称为完成之前，拿着那份意图去读无值的追踪。
