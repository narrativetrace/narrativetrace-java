# 选择集成方式

[English](../choosing-an-integration.md) | [Español](../es/eligiendo-una-integracion.md) | [Português](../pt-BR/escolhendo-uma-integracao.md) | **简体中文**

NarrativeTrace 只有一种捕获模型——一个通过流水线发布的进入/退出事件——但可以
通过五种不同的接入机制到达它。这一页回答"我到底需要哪个模块",先给出一张
速查表,再给出一张决策图,最后列出每条路径各自的注意事项。

## 你想要... / 从这里开始...

| 你想要 | 从这里开始 |
|---|---|
| 在测试里得到追踪,接线最少 | Gradle 插件 + `narrativetrace-junit5` |
| 同样的效果,但在 JUnit 4 上 | `narrativetrace-junit4` |
| 在纯 Java 里精确选择要包装什么 | `narrativetrace-proxy`(JDK 动态代理) |
| Spring Bean 自动被追踪 | `narrativetrace-spring` |
| 生产环境中 Spring HTTP 请求的生命周期 | `narrativetrace-spring-web`(接入 `narrativetrace-servlet`) |
| 任意 servlet 应用,不用 Spring | `narrativetrace-servlet` |
| Micronaut 的 Bean 与请求 | `narrativetrace-micronaut` + `narrativetrace-micronaut-http` |
| **零代码改动**——一个你不能或不想修改的应用 | `narrativetrace-agent`(Java Agent) |
| 跨线程的异步可见性(`@Async`、Reactor、executor) | `narrativetrace-micrometer`,或手动使用 `ContextSnapshot` |
| 在生产日志流中看到追踪 | `narrativetrace-slf4j` |
| OpenTelemetry span | `narrativetrace-opentelemetry` |

这与[根 README](../../自述文件.md#选择你的集成方式)里的矩阵是同一张;它也放
在这里,作为下面决策图与详细说明的锚点。

## 这个决策

这一页据以扩展的那份报告最初提出的图比下面这张更短——它把"不是
Spring/Micronaut 应用"当成了走向 Agent 的唯一理由。但框架集成实际的工作方
式并非如此:`narrativetrace-spring` 与 `narrativetrace-micronaut` 都用与
`narrativetrace-proxy` 相同的 JDK 动态代理来包装 Bean,所以一个没有接口的
Spring Bean,会像普通代理目标一样被跳过(已对照 `spring-integration-guide.md`
与 `micronaut-integration-guide.md` 验证过:两者都写明"Bean 必须至少实现一
个接口")。下面的图里包含了这条分支。

```text
你能控制对象是怎么构造出来的吗(纯 Java、一个测试)?
   |
   +-- 能  --> 这个服务实现了接口吗?
   |             |
   |             +-- 是 --> JDK 动态代理(narrativetrace-proxy)
   |             +-- 否 --> Java Agent(字节码插桩,
   |                        不需要接口)
   |
   +-- 不能 --> 它是 Spring 或 Micronaut 的 Bean 吗?
                 |
                 +-- 是 --> 这个 Bean 实现了接口吗?
                 |             |
                 |             +-- 是 --> 框架集成
                 |             |         (narrativetrace-spring /
                 |             |          narrativetrace-micronaut)
                 |             +-- 否 --> Java Agent
                 |
                 +-- 否 --> Java Agent(零代码改动)
```

两条路径最终都汇聚到 Agent,原因是同一个:它是这里唯一一个直接对字节码插
桩、因而完全不需要问"有没有接口"这个问题的机制。代价是 Agent 没有等价于
Spring `basePackages` 排除粒度的能力,也没有代理那种按调用逐一选择的方式
——见下面的注意事项,以及[与其他包装器叠加](#与其他包装器叠加),了解它与
另一个同样包装了相同类的机制叠加时会发生什么。

## 每条路径共有的一点

全部五种接入机制都通过同一个 `EventPipeline`
(`ai.narrativetrace.core.pipeline`)发布;没有哪一种定义了自己的"被捕获调
用"概念。选择一种集成,回答的始终是*调用是如何被包装的*,而不是一旦包装完
成后会记录什么——一次规范捕获供给每一条渲染路径(面向人类的详情、对 AI 安
全的结构、OpenTelemetry span、聚合),它们因此靠构造本身保持一致,而不是
靠约定。

## 每条路径的注意事项

- **JDK 动态代理**——目标必须实现传给 `NarrativeTraceProxy.trace(...)` 的
  接口,否则调用会在包装处抛出 `ClassCastException`。只有接口方法可见;
  直接在具体实例上发起的调用会完全绕过代理。
- **Spring / Micronaut**——同样的接口要求,但静默生效:没有接口的 Bean 会
  被原样保留,而不是报错。基础包只能用来包含,不能排除。
- **Java Agent**——匹配到的包下,每一个非私有、非抽象的方法都会被插桩;
  目前没有按方法关闭的选项,也没有排除列表(`AgentConfig` 只解析
  `packages`、`loggerName`、`level`、`loggingJars`——没有别的)。包匹配会
  识别分隔符,所以 `com.acme` 永远不会匹配到 `com.acmeExtra`。在 classpath
  上没有日志提供方的宿主上(最常见的是裸应用服务器),Agent 在你添加一个
  提供方之前不会叙述任何东西;见
  [故障排查](故障排查.md#agent-已追踪但日志中没有任何输出)。
- **跨线程工作**——上面五条路径没有一条会自动把异步/executor 线程上的调
  用并入父追踪。手动使用 `ContextSnapshot.wrap(...)`,或者向 Micrometer
  注册 `NarrativeTraceThreadLocalAccessor`。

## 与其他包装器叠加

NarrativeTrace 很少是唯一包装某个方法的东西:AOP 代理、契约库、容器拦截
器和其他可观测性 Agent 都可能挂到同一次调用上。以下三条规则在上面每一种
接入机制上都成立:

- **每次业务边界穿越对应一个追踪帧。** 目标是叙述你的代码发起的调用,而
  不是它周围的机制性代码——桥接方法、容器生成的视图桩、其他库生成的装饰
  器,或者 NarrativeTrace 自己的渲染逻辑,都不是叙述的对象。
- **嵌套顺序会改变追踪*读起来*的样子,但绝不会改变它*返回或抛出*的内
  容。** 哪个包装器在更内层、哪个在更外层,可能改变记录下来的调用树形
  状,但记录在所有路径上都做了异常隔离,绝不会替换结果——调用方看到的业
  务结果或异常,始终是真实的那一个。
- **范围控制处处都只有包含匹配。** Agent 的 `packages=`、Spring 和
  Micronaut 的基础包,以及代理显式指定的目标接口,都遵循分隔符边界
  (`com.acme` 永远不会匹配到 `com.acmeExtra`),而且都还没有排除列表——
  只要一个类落在你匹配的包里,不论它是你自己的代码还是另一个库的代码,
  都会被包装。

## 平台上限

上面每条路径都假定运行在服务器或桌面 JVM 上。今天还不支持 Android(三处
彼此独立的机制——SPI 发现、SLF4J listener 查找、以及基于反射的值渲
染——在 R8/ProGuard 下都会静默降级,而不是明确报错),GraalVM 原生镜像也
未经测试(代理与 Agent 路径都依赖反射,且没有随包发布的可达性元数据)。完
整细节见
[安装指南 § 兼容性](安装指南.md#兼容性)。
