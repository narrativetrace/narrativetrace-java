# 故障排查

[English](../troubleshooting.md) | [Español](../es/solucion-de-problemas.md) | [Português](../pt-BR/solucao-de-problemas.md) | **简体中文**

症状 → 原因 → 解决办法,覆盖大家实际会遇到的失败模式。有些条目是完整的
解释;有些则指向已经带着详细说明的那份指南,而不是在这里重复一遍——一个
事实只有一个家。

## 参数显示为 `arg0`、`arg1`

**原因:** 缺少 `-parameters` 编译器参数,所以编译出来的类里没有真正的参
数名可供 NarrativeTrace 读取。

**解决办法:**

```kotlin
tasks.withType<JavaCompile> {
    options.compilerArgs.add("-parameters")
}
```

Gradle 插件会自动加上这一项——这条只在手动搭建时才用得上。

## `Cannot create Launcher without at least one TestEngine`,或 `Could not start Gradle Test Executor 1: Failed to load JUnit Platform`

**原因:** `useJUnitPlatform()` 需要测试运行时类路径上同时存在 JUnit 5
engine 和 `org.junit.platform:junit-platform-launcher`。Gradle 8
在只声明了 engine 的情况下会自己补上一个 launcher 版本——这是一个已废弃
的行为,每次运行都会给出警告——而 Gradle 9 彻底移除了这种自动管理,于是
测试*进程*会在任何 engine、扩展或测试类运行之前就失败。已在真实的
Gradle 9.0.0 构建上复现:上面第二条消息就是它的原文。

**解决办法:**

```kotlin
dependencies {
    testRuntimeOnly("org.junit.jupiter:junit-jupiter-engine:5.11.4")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher:1.11.4")
}
```

Gradle 插件会自动加上这两项 *(since 0.2.2, unreleased)*——这条只在手动搭建时才用得上。

## 没有追踪输出文件

**原因:** 输出默认会写入 *(since 0.2.2, unreleased)* `build/narrativetrace`,所以文件缺失通常是以下
原因之一:某处设置了 `narrativetrace.output=false`(`junit-platform.properties`、
系统属性,或 Gradle 插件的 `enabled.set(false)`);追踪本身是空的,因为没有
调用经过被追踪的代理/Agent;或者 `narrativetrace.outputDir` 指向了你正在
查看的目录之外的地方。

**解决办法:** 确认该属性没有被设为 `false`,并检查
`build/narrativetrace/`(或你配置的 `narrativetrace.outputDir`)——每个属性
及其默认值见[配置指南](配置指南.md)。

## 我的终端里什么都看不到

**原因:** 每个测试的摘要和套件的footer都写到了测试进程的标准输出。
Gradle 的 `test` 任务默认会把它捕获进 XML/HTML 报告——单独一条
`./gradlew test` 在普通终端里什么都不会显示,即便 `build/narrativetrace/`
下的每个文件其实都正确写出了。

**解决办法:** 在 `test` 任务上打开标准输出流的日志:

```kotlin
tasks.test {
    testLogging.showStandardStreams = true
}
```

这是 Gradle 的行为,不是 NarrativeTrace 做的事——同样的说明也出现在
JUnit 4 的配方里,见
[安装指南 § 选项 D](安装指南.md#选项-djunit-4-自动上下文--追踪输出)。

## 代理抛出 `ClassCastException`

**原因:** 目标没有实现传给 `NarrativeTraceProxy.trace(...)` 的接口。

**解决办法:** 确认具体的类实现了那个接口,并且传入接口的 `Class`,而不
是实现类的。

## Spring Bean 没有被追踪

**原因:** 要么这个 Bean 所在的包不在 `basePackages` 里,要么这个 Bean 没
有实现任何接口——`narrativetrace-spring` 用的是与 `narrativetrace-proxy`
相同的 JDK 动态代理,它没法包装一个没有接口的类。没有接口的 Bean 会被静
默地原样保留;这不是一个错误。

**解决办法:** 把这个包加到 `@EnableNarrativeTrace(basePackages = ...)`
里,如果这个 Bean 还没有接口,给它一个。

## Micronaut HTTP 过滤器没有注入用户上下文

**原因:** 一个实现了 `RequestContextProvider` 的 Bean,写错了类型。
NarrativeTrace 随包发布了两个名字很像的接口:
`ai.narrativetrace.api.export.RequestContextProvider<REQUEST>`(通用、与
框架无关,servlet 过滤器和 Spring Web 绑定到 `HttpServletRequest` 时用的
就是它),以及一个 Micronaut 专属的、HTTP 过滤器实际查找的接口。一个实现
了 API jar 里那个类型的 Bean,会被静默地判定为不合格——过滤器什么都不注
入,运行时没有用户上下文,而且完全不会报错。症状是每个 span 都显示空的
`enduserId`/`tenantId` 字段。

**解决办法:** 实现 Micronaut 的那个类型,而不是 API jar 里的那个。完整
细节——包括为什么这两个类型要分开——见
[Micronaut 集成指南](Micronaut集成指南.md)与
[API Surface](../api-surface.md)。

## 清晰度评分看起来不对

**原因:** 通常是 NLP 分析标记出的一个泛化命名——`get`、`set`、
`process`、`handle`、`data`、`info`、`temp` 以及类似的词,不管上下文如
何,评分都会偏低。

**解决办法:** 查看 `clarity-report.md` 里的问题列表,把被标记的名字换成
一个领域专属的名字(`getData()` → `fetchOrderHistory()`)。完整的评分模
型见[清晰度指南](清晰度指南.md)。

## 跨线程的追踪是空的

**原因:** `captureTrace()`/`events()` 是按线程作用域的——它们只返回调用
它们的那个线程的追踪。要么上下文从未被传播到异步线程,要么
`captureTrace()` 是在与记录事件的线程不同的另一个线程上调用的。

**解决办法:**

```java
var snapshot = context.snapshot();
executor.submit(snapshot.wrap(() -> service.process()));
```

或者向 Micrometer 注册 `NarrativeTraceThreadLocalAccessor` 来实现自动传
播。如果你只需要派生出去的那部分工作本身,就在任务内部、在负责记录的那
个线程上调用 `captureTrace()`。

## Agent 没有插桩类

**原因:** `packages=` 过滤器没有匹配上,或者边界规则和你预期的不一
样——`com.example` 会匹配 `com.example.*`,但永远不会匹配
`com.exampleExtra`。

**解决办法:** 检查 `packages=` 参数;通配符(`com.example.*`)和多个包
(用分号分隔,`packages=com.a.*;com.b.*`)都支持。没有排除列表——只有包
含。

## Agent 已追踪但日志中没有任何输出

**原因:** Agent 刻意不带任何自己的 SLF4J 提供方——一个最小化的宿主(最
常见的是没有可达 classpath 的应用服务器)没有任何东西可供叙述写入,所以
SLF4J 会记录一次性的警告,并退回到一个空操作的 logger。没有任何东西是坏
的:`captureTrace()` 依然会返回追踪,`build/narrativetrace/` 下的文件(如
果输出是开着的)也不受影响——只有实时的日志叙述是静默的。

**解决办法:** 把一个提供方放到 classpath 上(`logback-classic`、
`slf4j-simple`……),或者对一个没有可达 classpath 的宿主传入
`loggingJars=/path/to/provider.jar`。如果是故意想让叙述静默,改用
`loggerName=`(留空)或 `-Dnarrativetrace.narration=off`。完整配方见
[安装指南 § 叙述需要 SLF4J 提供方——Agent 从不自带](安装指南.md#叙述需要-slf4j-提供方--代理从不自带)。

## `@NotTraced` 编译失败:"package ai.narrativetrace.api.annotation does not exist"

**原因:** Gradle 插件默认的 `scope` 是 `"test"`,所以
`narrativetrace-api`——每一个注解所在的地方——只挂在 `testImplementation`
上。从 `src/main/java` 下的一个类引用 `@NotTraced`(或
`@Narrated`、`@OnError`、`@NarrativeSummary`),会在任何测试跑起来之前就
编译失败。

**解决办法:** 把 API jar 加到 `compileOnly` 上(它自身不带任何运行时依
赖):

```kotlin
dependencies {
    compileOnly("ai.narrativetrace:narrativetrace-api:0.2.1")
}
```

或者,如果 NarrativeTrace 本来就打算跑在生产环境里,就设置
`scope.set("production")`。见
[配置指南 § Gradle 插件 DSL](配置指南.md#gradle-插件-dsl),那里记录了
`scope` 的用法。

## 审批模式写出了 `.received.nt`

**原因:** 这是预期中的行为,不是一次失败——要么这个场景还没有
`.approved.nt` 基线,要么一个通过的测试的结构已经和已提交的版本产生了偏
移。

**解决办法:** 审阅 `.received.nt` 的 diff,如果新的形状是对的,就把它提
升为基线:

```bash
./gradlew approveNarratives
```

永远不要不看 diff 就手动把它改名放进去——那正是审批模式存在的意义:强
制先看一眼再批准。完整的格式与文件布局见
[结构化追踪格式](结构化追踪格式.md);每天该拿每个文件怎么办,见
[应提交的内容](应提交的内容.md)。
