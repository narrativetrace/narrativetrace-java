# 前 10 分钟

[English](../first-10-minutes.md) | [Español](../es/primeros-10-minutos.md) | [Português](../pt-BR/primeiros-10-minutos.md) | **简体中文**

一个极小的服务,一个 JUnit 测试,八个步骤。下面的每一条命令都真实运行在这
个版本的仓库上——文件路径、清晰度评分、断言消息以及 `[REDACTED]` 标记都是
真实输出,不是示意图。你机器上唯一会不一样的是耗时(`ms`)和两个单词组成的
`trace_name`,二者都是每次运行时重新生成的。

Java 17+、Gradle 插件、JUnit 5。如果你还没跑过演示,从仓库根目录执行
`./demo.sh --example ecommerce --no-pause` 会更快——这一页是给你想在*自己的*
代码上看看效果时用的。

## 1. 添加插件

```kotlin
// build.gradle.kts
plugins {
    id("ai.narrativetrace") version "0.2.0"
}
```

这就是全部的依赖配置:插件会添加 `narrativetrace-core`、`-proxy`、
`-clarity`、`-diagrams` 与 `-junit5`,`-parameters` 编译器参数,以及
JUnit Platform 引擎。

## 2. 添加一个服务接口及其实现

```java
// src/main/java/com/example/orders/OrderService.java
package com.example.orders;

public interface OrderService {
    String placeOrder(String customerId, String productId, int quantity);
}
```

```java
// src/main/java/com/example/orders/DefaultOrderService.java
package com.example.orders;

public class DefaultOrderService implements OrderService {
    @Override
    public String placeOrder(String customerId, String productId, int quantity) {
        return "ORD-" + customerId + "-" + productId + "-" + quantity;
    }
}
```

之所以用接口,是因为本教程用到的 JDK 动态代理只能包装接口。对于没有接口的
服务,[集成矩阵](选择集成方式.md)给出了对应的路径。

## 3. 添加一个 JUnit 测试

```java
// src/test/java/com/example/orders/OrderServiceTest.java
package com.example.orders;

import ai.narrativetrace.core.context.NarrativeContext;
import ai.narrativetrace.junit5.NarrativeTraceExtension;
import ai.narrativetrace.proxy.NarrativeTraceProxy;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;

@ExtendWith(NarrativeTraceExtension.class)
class OrderServiceTest {
    @Test
    void customerPlacesOrder(NarrativeContext context) {
        OrderService service = NarrativeTraceProxy.trace(
            new DefaultOrderService(), OrderService.class, context);

        service.placeOrder("C-1234", "SKU-KB", 2);
    }
}
```

`NarrativeTraceExtension` 注入 `context`;`NarrativeTraceProxy.trace(...)`
把真正的实现包装在接口背后,于是每一次对 `service` 的调用都会被捕获。

## 4. 运行测试套件

```bash
./gradlew test
```

输出落在 `build/narrativetrace/` 中——正是插件承诺的形状,不多不少,每个
场景每种格式各一个文件:

```text
build/narrativetrace/
   |
   +-- traces/OrderServiceTest/customer_places_order.md    人类可读叙事
   +-- traces/OrderServiceTest/customer_places_order.json  同一条追踪,规范 JSON
   +-- diagrams/OrderServiceTest/customer_places_order.mmd Mermaid 时序图
   +-- structural/OrderServiceTest/customer_places_order.nt 无值形状(最近一次绿色基线)
   +-- clarity-report.md                                   整个套件的命名反馈
   +-- clarity-results.json                                同样的评分,供 clarityCheck 使用
```

`OrderServiceTest.customerPlacesOrder` 变成了
`customer_places_order`——测试方法名,人性化并转换为 slug。没有其他需要配置
的东西。

> NarrativeTrace 还会向测试进程的标准输出打印一份实时摘要,而 Gradle 默认
> 只把它路由进 XML/HTML 报告——单独一条 `./gradlew test` 不会在你的终端里
> 显示任何东西,尽管上面那些文件其实都正确写出了。要实时看到它,见
> [故障排查](故障排查.md#我的终端里什么都看不到)。

## 5. 打开叙事文件

`build/narrativetrace/traces/OrderServiceTest/customer_places_order.md`:

```markdown
---
type: trace
scenario: Customer places order
entry_point: OrderService.placeOrder
duration_ms: 3.973
trace_id: be4e2e8ea4dfcb18ccc43fbb59223bcc
trace_name: rural ivory heaps
method_count: 1
error_count: 0
---

## Trace: OrderService.placeOrder

**Scenario:** Customer places order
**Duration:** 3.973ms | **Result:** PASSED

### Call Flow

- **OrderService.placeOrder**(customerId: `"C-1234"`, productId: `"SKU-KB"`, quantity: `2`) → `"ORD-C-1234-SKU-KB-2"` — 3.973ms
```

调用流程里的每一个值——参数值、返回值——都来自你真正发起的那次调用。没有
任何一处是手写的。

## 6. 把 `placeOrder` 改名为 `process`,看清晰度下降

命名质量是被测量出来的,不是靠假设。改名之前,`clarity-report.md` 写的是:

```markdown
| Scenario | Score |
|----------|-------|
| Customer places order | 0.89 |

| Element | Score | Note |
|---------|-------|------|
| `OrderService.placeOrder` | 0.81 | Standard verb 'place' + broad noun 'order' |
```

把方法(接口、实现以及调用点)改名为 `process`,再次运行 `./gradlew test`:

```markdown
| Scenario | Score |
|----------|-------|
| Customer places order | 0.68 |

| Category | Score | Weight | Weighted |
|----------|-------|--------|----------|
| Method Names | 0.10 | 0.30 | 0.03 |
| Class Names | 0.91 | 0.20 | 0.18 |
| Parameter Names | 0.92 | 0.25 | 0.23 |
| Structural | 1.00 | 0.15 | 0.15 |
| Cohesion | 0.90 | 0.10 | 0.09 |
| **Overall** | **0.68** | | |

| Severity | Category | Element | Suggestion |
|----------|----------|---------|------------|
| HIGH | method-name | `OrderService.process` | Use a domain-specific verb+noun (e.g., calculateTotal, reserveInventory) |
```

同样的调用、同样的值、除了名字之外一切都没变——总体评分从 0.89 掉到
0.68,方法名这一维度单独从 0.81 掉到 0.10,并且出现了一条 HIGH 严重级别的
问题。这正是 `clarityCheck` 背后的机制:在 CI 中设置阈值,一个泛化的命名会
让构建失败,而不是悄悄地混进去。完整的评分模型见
[清晰度指南](清晰度指南.md)。继续之前把名字改回 `placeOrder`(或者改成更具
体的名字)。

## 7. 添加 `@NotTraced` 并查看脱敏效果

```java
public interface OrderService {
    String placeOrder(
        String customerId, String productId, int quantity, @NotTraced String paymentToken);
}
```

因为插件默认的 `scope` 是 `"test"`,NarrativeTrace 的 jar 包——包括
`@NotTraced` 所在的 `narrativetrace-api`——只挂在 `testImplementation` 上,
不在主编译 classpath 上。从 `src/main/java` 下的接口引用这个注解,会让
`./gradlew test` 在还没跑任何测试之前就*编译*失败,报
"package ai.narrativetrace.api.annotation does not exist"。把 API jar 加到
`compileOnly` 即可修复(它自身不带任何运行时依赖):

```kotlin
dependencies {
    compileOnly("ai.narrativetrace:narrativetrace-api:0.2.0")
}
```

在测试里传入一个令牌(`service.placeOrder("C-1234", "SKU-KB", 2,
"tok_live_51H8x9J")`)再运行一次。这次的追踪:

```text
- **OrderService.placeOrder**(customerId: `"C-1234"`, productId: `"SKU-KB"`, quantity: `2`, paymentToken: `[REDACTED]`) → `"ORD-C-1234-SKU-KB-2"` — 9.428ms
```

参数名依然出现——你能看得出*确实*传了一个令牌——但它的值永远不会落到磁盘
上。脱敏还覆盖了哪些内容、以及关闭脱敏的两种方式,见
[隐私与脱敏](隐私与脱敏.md)。

## 8. 打开审批模式,看看 `.received.nt`

```kotlin
narrativeTrace {
    approval.set(true)
}
```

在还没有任何已审批基线的情况下运行 `./gradlew test`,原本会通过的测试还是
失败了:

```text
java.lang.AssertionError: No approved narrative for scenario "Customer places order".
Received: src/test/narratives/OrderServiceTest/customer_places_order.received.nt
Review it and approve via the approveNarratives task (or rename it to customer_places_order.approved.nt).
```

`customer_places_order.received.nt` 保存的是这次调用的无值形状:

```text
scenario: Customer places order

- OrderService.placeOrder(customerId, productId, quantity, paymentToken) → value
```

审阅它,然后把它提升为基线:

```bash
./gradlew approveNarratives
# Approved: src/test/narratives/OrderServiceTest/customer_places_order.approved.nt
```

现在 `./gradlew test` 会通过。从此往后,这个场景发生的任何结构性变化——新
增一次调用、丢失一次调用、结果种类发生变化——都会让构建带着一份可读的 diff
失败,直到有人审阅并重新批准它。完整细节,包括什么才算"结构性变化",见
[结构化追踪格式](结构化追踪格式.md)。
