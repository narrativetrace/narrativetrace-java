# NarrativeTrace Java 配置指南

[English](../configuration-guide.md) | [Español](../es/guia-de-configuracion.md) | **简体中文**

本指南介绍 NarrativeTrace Java 的运行时配置与测试配置。
想了解哪种配置属于流程的哪个阶段 —— 开发、CI/验收、生产 ——
请参阅[生命周期指南](生命周期指南.md)。

## 配置途径

NarrativeTrace 提供六种配置途径:

| 途径 | 机制 | 适用场景 |
|---|---|---|
| Gradle 插件 | `build.gradle.kts` 中的 `narrativeTrace { }` DSL | Gradle 项目(推荐) |
| JUnit 5 | `junit-platform.properties` | 测试期的追踪输出 |
| 纯 Java / Agent | classpath 上的 `narrativetrace.properties` | 独立应用、Agent |
| Gradle(手动) | `gradle.properties` + 构建脚本转发 | 未使用插件的 Gradle 项目 |
| Spring | `@EnableNarrativeTrace` 注解 | Spring 应用 |
| Micronaut | 通过 `@ConfigurationProperties` 读取 `application.yml` | Micronaut 应用 |

所有途径都支持以系统属性(`-D` 参数)作为最高优先级的配置来源进行覆盖。

## Gradle 插件 DSL

Gradle 插件(`ai.narrativetrace`)会自动完成所有配置。应用插件后,可按需自定义:

```kotlin
plugins {
    id("ai.narrativetrace") version "0.2.1"
}

// 零配置即可工作, 一切都有合理的默认值:
narrativeTrace { }

// 完整配置面:
narrativeTrace {
    enabled.set(true)                          // 默认: true
    mode.set("proxy")                          // "proxy" (默认) | "agent" | "spring"
    testFramework.set("junit5")               // "junit5" (默认) | "junit4"
    scope.set("test")                          // "test" (默认) | "production"
    format.set("markdown")                     // "markdown" | "text" | "mermaid" | "plantuml"
    tracingLevel.set("DETAIL")                 // "OFF" | "ERRORS" | "SUMMARY" | "NARRATIVE" | "DETAIL"
    outputDir.set(layout.buildDirectory.dir("narrativetrace"))
    glossary.set(false)                        // 默认: false — 套件结束时收集 glossary.json
    approval.set(false)                        // 默认: false — 将结构与已提交的基线进行核对
    approvedDir.set(layout.projectDirectory.dir("src/test/narratives"))

    modules {                                  // 细粒度按需启用 (全部默认为 false)
        slf4j.set(false)
        micrometer.set(false)
        servlet.set(false)
        springWeb.set(false)                   // 隐含启用 servlet
    }

    agent {                                    // 仅在 mode = "agent" 时相关
        packages.set(listOf("com.example.app"))
    }

    clarity {
        minScore.set(0.80)                     // 默认: 0.0 (不设门禁)
        maxHighIssues.set(0)                   // 默认: Integer.MAX_VALUE (不设门禁)
        maxSuiteIssues.set(0)                  // 默认: Integer.MAX_VALUE (仅告警)
        warnOnly.set(false)                    // 默认: false
    }
}
```

### 插件做了什么

| 动作 | 详情 |
|---|---|
| 添加 `-parameters` 编译器参数 | 作用于所有 `JavaCompile` 任务;若已存在则跳过 |
| 添加依赖 | 依据 `mode`、`modules` 与 `testFramework`;版本从插件 JAR 自动检测 |
| 设置测试 JVM 属性 | `narrativetrace.output=true`、`narrativetrace.outputDir`,并可选设置 `narrativetrace.format`、`narrativetrace.level`、词汇表属性对(`glossary=true`)以及审批属性对(`approval=true`) |
| 注册 `clarityCheck` 任务 | 读取 `clarity-results.json`,执行阈值门禁,并接入 `check` 生命周期 |
| 注册 `clarityScan` 任务 | 从已编译的类进行独立的清晰度分析(无需运行测试) |
| 注册 `glossaryScan` 任务 | 从已编译的类独立收集领域词汇表,包括注解模板 |
| 注册 `approveNarratives` 任务 | 将已审阅的 `*.received.nt` 叙事提升为 `*.approved.nt` 基线(审批模式) |
| 配置 Agent 的 JVM 参数 | 当 `mode = "agent"` 时:解析 Agent JAR,并为 Test 任务添加 `-javaagent` |

### 拦截模式

| 模式 | 添加的依赖(除 core + clarity + diagrams + 测试框架之外) |
|---|---|
| `proxy`(默认) | `narrativetrace-proxy` |
| `agent` | `narrativetrace-agent`(使用单独的 configuration 以解析 JAR) |
| `spring` | `narrativetrace-spring` + `narrativetrace-proxy` |

### 模块按需启用

| 开关 | 构件 | 说明 |
|---|---|---|
| `modules.slf4j` | `narrativetrace-slf4j` | SLF4J 桥接 |
| `modules.micrometer` | `narrativetrace-micrometer` | 跨线程传播 |
| `modules.servlet` | `narrativetrace-servlet` | Servlet 过滤器 |
| `modules.springWeb` | `narrativetrace-spring-web` + `narrativetrace-servlet` | 自动加上 servlet |

### 依赖作用域

| 作用域 | 库依赖 | 测试框架依赖 |
|---|---|---|
| `test`(默认) | `testImplementation` | `testImplementation` |
| `production` | `implementation` | `testImplementation`(始终如此) |

### 禁用插件

要完全禁用插件(例如在某个子项目中),设置 `enabled.set(false)`。此时不会注册任何任务、不会添加任何依赖、也不会设置任何编译器参数。

```kotlin
narrativeTrace {
    enabled.set(false)
}
```

### 清晰度阈值

`clarityCheck` 任务读取 `build/narrativetrace/clarity-results.json`(由 JUnit 扩展在 `test` 期间生成),并执行已配置的阈值门禁。它作为 `./gradlew check` 的一部分自动运行。

- **`minScore`** —— 总体清晰度评分的下限(0.0–1.0)。任何低于该阈值的场景都会使构建失败。
- **`maxHighIssues`** —— 每个场景允许的 HIGH 严重级别问题数量上限。超出即构建失败。
- **`warnOnly`** —— 为 `true` 时,阈值违规只产生警告,而不会使构建失败。

如果 `clarity-results.json` 不存在(例如没有运行任何测试),该任务会静默通过。

### 版本解析

插件从其插件 JAR 自动检测自身版本(没有对应的 DSL 属性)。所有受管理的依赖都使用同一版本。不存在 `manageDependencies` 属性 —— 只要 `enabled=true`,插件就会依据 mode/modules/scope 管理依赖。想要完全手动控制的用户可以设置 `enabled.set(false)` 并自行接线。

关于插件的完整参考,包括常用配方、Groovy DSL 与校验细节,请参阅 [Gradle 插件指南](Gradle插件指南.md)。

## 1. 追踪级别(`NarrativeTraceConfig`)

`ThreadLocalNarrativeContext` 使用 `NarrativeTraceConfig`,其默认值为 `DETAIL`。

```java
var config = new NarrativeTraceConfig(TracingLevel.NARRATIVE);
var context = new ThreadLocalNarrativeContext(config);
```

可用级别:

| 级别 | 行为 |
|---|---|
| `OFF` | 不捕获任何追踪 |
| `ERRORS` | 仅捕获异常路径 |
| `SUMMARY` | 捕获根入口、最深的叶节点与完整的异常链 |
| `NARRATIVE` | 捕获完整调用流程,但不记录参数值;返回值在所有激活级别都会渲染(这是一项文档化的承诺——返回值是叙事的核心内容)|
| `DETAIL` | 捕获完整调用流程,包含参数值与返回值 |

支持在运行时切换级别:

```java
config.setLevel(TracingLevel.ERRORS);
```

## 2. JUnit 5 配置(`junit-platform.properties`)

JUnit 扩展使用 `ExtensionContext.getConfigurationParameter()`,它按以下顺序解析取值:

1. 系统属性(最高 —— CLI 的 `-D` 参数依然有效)
2. 测试 classpath 上的 `junit-platform.properties`
3. 硬编码默认值(最低)

### 属性

| 属性 | 取值 | 默认值 |
|---|---|---|
| `narrativetrace.output` | `true` / `false` | `true` *(since 0.2.2, unreleased)* |
| `narrativetrace.outputDir` | 任意可写路径 | `build/narrativetrace` |
| `narrativetrace.format` | `markdown`、`text`、`mermaid`、`plantuml` | `markdown` |
| `narrativetrace.unfolded` | `true` / `false` | `false` |
| `narrativetrace.glossary` | `true` / `false` | `false` |
| `narrativetrace.glossaryDir` | 任意可写路径 | 工作目录 |
| `narrativetrace.canonicalJson` | `true` / `false` | `false` |
| `narrativetrace.structuralJson` | `true` / `false` | `false` |
| `narrativetrace.approval` | `true` / `false` | `false` |
| `narrativetrace.approvedDir` | 已提交基线所在目录 | `src/test/narratives` |
| `narrativetrace.bufferCapacity` | 测试上下文事件环形缓冲区的槽位数 | `8192` |

`narrativetrace.bufferCapacity` 用于设定扩展**为每个测试方法**构造的那个上下
文的事件环大小。它默认取 8,192 个槽位而不是运行时的 65,536,因为一个测试跟踪
的是几十次调用,而不是几万次,而环是在构造时就整体分配的 —— 采用运行时的默认
值,每个测试方法要为没有任何测试能用到的槽位付出 1.75 MB 与约 1.5 ms。取
8,192 时是 224 kB。

这是同一个旋钮的 JUnit 5 写法;运行时范围的 `narrativetrace.buffer.capacity`
(系统属性或 `narrativetrace.properties` 条目)优先级更高,因为部署方的设置压
过集成方的默认值。运行时不会检测 JUnit —— 是扩展在自己的代码里显式传入了它的
选择。

如果某个测试确实超过了 8,192 个事件,超出的部分会被丢弃,并且会说出来:它写出
的每一份叙事都会带上一行页脚,写明数量以及应当调高的属性。只想修测试就调这
个,想到处生效就调运行时那个键。

术语表采集默认关闭,因为它会改写位于构建目录**之外**的 `glossary.json` 与
`glossary.md` —— 它们是提交入库、经过评审的产物,而不是构建输出。
`narrativetrace.glossaryDir` 指定存放这两个文件的目录;Gradle 插件会把它设置
为仓库根目录,这在多模块构建中很重要:测试任务的工作目录是子项目,而术语表
是每个仓库仅有一份的文件。

即使采集处于关闭状态,`narrativetrace.glossaryDir` 也会被读取:已提交的
`glossary.json` 就是清晰度评分所使用的项目词汇表(参见
[清晰度指南](清晰度指南.md))。读取不会改动磁盘上的任何内容,因此无需显式开启;
没有该文件的仓库只按内置词典评分。

`narrativetrace.canonicalJson` 还会在每个追踪文件旁写出
`<test>.canonical.json`(模式 1.1 的条目数组)——面向规范模式消费方
(NarrativeTrace 的其他实现、一致性 fixture)的机器工件。

`narrativetrace.structuralJson` 还会在每个追踪文件旁写出
`<test>.structural.json`:同样是模式 1.1 的条目数组,但所有运行时值字段
均被略去(参数值为 `[ELIDED]`,返回值与异常消息为 null)——即 ADR-002
第 1 级的 AI 安全结构化产物。两个开关相互独立,可在同一次运行中组合使用。

`narrativetrace.unfolded` 会**关闭 Markdown 叙事中的循环折叠**。默认情况下,
一串连续的同形状兄弟调用会渲染成完整的第一次迭代加上一行摘要 ——
`×2 more: ‹Taxi›, #3 sku=` `` `"TENT"` `` ` — same flow (validate ✓ →
record ✓)`。这一行会给每一次被折叠的迭代命名:当区分它的参数有身份标签时用
标签,否则用位置加上参数本身,这样被省略的迭代仍然是可达的。当你需要每次迭代
*完整的*子树和它的全部值时,设置 `narrativetrace.unfolded=true`,每一次迭代
都会完整渲染。仅限 Markdown —— 其他格式都不折叠,而规范 JSON 始终携带每一次
迭代。配合 Gradle 插件时,像转发其他属性一样转发它:

```kotlin
tasks.withType<Test> { systemProperty("narrativetrace.unfolded", "true") }
```

`narrativetrace.approval` 开启审批模式:测试**通过**后,场景的无值结构
(与 `.nt` 产物相同的渲染)会与已提交的基线
`<approvedDir>/<TestClassSimpleName>/<artifact_name>.approved.nt` —— 与其他
每个按测试产物相同的产物身份,因此运行多次的方法每次调用都有自己的基线
进行核对。基线缺失或结构存在差异都会使测试失败并给出可读的 diff,同时把
当前结构作为 `*.received.nt` 写到基线旁;审阅后用 Gradle 的
`approveNarratives` 任务接受它(或手动重命名)。失败的测试从不核对 ——
其结构处于中途状态,不应扰动 received 文件。Gradle 插件会通过其
`approval` / `approvedDir` DSL 设置这两个属性。

### 基于文件的配置(推荐)

输出默认就会写入 —— 不需要任何文件去开启它。只有想更改格式或退出时,
才需要在 `src/test/resources/junit-platform.properties` 放置一个文件:

```properties
narrativetrace.output=false
```

无需在 Gradle 中接线 `systemProperty()`。该文件仅用于测试,绝不会影响生产环境。

### CLI 覆盖

系统属性仍然可以作为覆盖手段:

```bash
./gradlew test -Dnarrativetrace.output=false
./gradlew test -Dnarrativetrace.format=text
./gradlew test -Dnarrativetrace.outputDir=out/narrative
```

### Gradle CLI 转发(可选)

仅当你想让 CLI 的 `-D` 参数经由 Gradle 传入 fork 出的测试 JVM 时才需要:

```kotlin
tasks.withType<Test> {
    System.getProperty("narrativetrace.output")?.let { systemProperty("narrativetrace.output", it) }
    System.getProperty("narrativetrace.outputDir")?.let { systemProperty("narrativetrace.outputDir", it) }
    System.getProperty("narrativetrace.format")?.let { systemProperty("narrativetrace.format", it) }
}
```

### 场景名称

扩展会从每个测试推导出人类可读的场景名称:

- `customerPlacesOrder()` → "Customer places order"
- `customer_places_order()` → "Customer places order"
- `@DisplayName("customer places order")` → "customer places order"(原样传递)

JUnit 的参数类型后缀(例如 `(NarrativeContext)`)会被自动剥除。

### 文件布局

基础布局:

- `<outputDir>/traces/<TestClassSimpleName>/<artifact_name>.<ext>`

`<artifact_name>` 是一次测试调用的**产物身份**:

- 普通测试方法就是其方法名的 slug —— `customerPlacesOrder` →
  `customer_places_order`。
- 会运行多次的方法(`@ParameterizedTest`、`@RepeatedTest`)会追加
  `-<序号>-<标签>`:从 1 开始的调用序号,补零到三位,然后是该次调用的
  显示名经过同一套 slug 规则的结果 ——
  `equipment_can_be_found-002-find_tent`。当标签的 slug 为空时会被省略,
  只留下 `equipment_can_be_found-002`。
- 之所以用 `-` 作分隔符,是因为 slug 的字母表是 `[a-z0-9_]`,永远产生不出
  连字符:一次调用的产物绝不会与普通方法的产物冲突,而且这个名字可以再拆
  回方法、序号与标签三部分。同一方法的两次调用序号必然不同,所以仅在路径
  无法承载的字符上有差别的显示名(`find/TENT` 与 `find TENT`)仍然会落到
  不同的文件上。
- 名字中没有任何部分会随运行或机器而变化,这正是每次调用的审批基线能够被
  提交进版本库的前提。名字超出文件系统限制时,截断发生在*方法*那一半,并
  追加完整 slug 的 Java `String.hashCode` 的八位十六进制字符;序号与标签
  永远不是被截掉的部分。

一次调用的每个按测试产物都共用这个名字:追踪文件、JSON 导出、图、结构化
产物,以及与它们放在一起提交的 `.approved.nt` 基线。

> `@ParameterizedTest(name = ...)` 模板会把参数插值进显示名,所以无值的 `.nt`
> 产物不用它作标题:一次调用的 `scenario:` 头是 `<人类可读的方法名> #<序号>`
> (`Equipment can be found #2`),而只运行一次的方法仍保留它一直用的显示名 *(since 0.2.2, unreleased)*。
> 产物的*文件名*和 `manifest.json` 确实带着显示名——文件名是在磁盘上区分两次
> 调用的东西,而清单同时索引带值的产物。不要把机密放进显示名模板。

当 `format=markdown` 时,扩展还会为每个测试写出:

- Mermaid 图:`<outputDir>/diagrams/<TestClassSimpleName>/<artifact_name>.mmd`
- JSON 导出:`<outputDir>/traces/<TestClassSimpleName>/<artifact_name>.json`
- 结构化产物:`<outputDir>/structural/<TestClassSimpleName>/<artifact_name>.nt`
  —— 无值的调用结构(格式规范:
  [structural-trace-format.md](../structural-trace-format.md))。磁盘上的
  该文件是**最近一次绿色运行的基线**:绿色运行会推进它,非绿色运行只与它
  比较、绝不覆盖它,因此每个 delta 读起来都是"自该场景上次通过以来发生了
  什么变化"。这里的"绿色"指的是整体裁决,而不只是断言 —— 测试通过、但其
  结构被审批**拒绝**的运行以红色告终,它的结构不会被写入。因此拒绝一次改动
  会让基线停在原处,而把改动还原后不会报出任何 delta

一个类中的所有测试完成后,扩展会写出:

- 运行清单:`<outputDir>/manifest.json` —— 每个被追踪的场景一行,按执行
  顺序排列,标明产生它的测试、方法运行多次时的调用序号,以及它拥有的每个
  产物(相对 `<outputDir>` 的路径)。当你知道场景、想找文件时,读的就是
  这个索引:
  ```json
  {
    "scenario": "find TENT",
    "testClass": "traildepot.CatalogTest",
    "testMethod": "equipmentCanBeFound",
    "invocation": 2,
    "artifacts": {
      "trace": "traces/CatalogTest/equipment_can_be_found-002-find_tent.md",
      "structural": "structural/CatalogTest/equipment_can_be_found-002-find_tent.nt"
    }
  }
  ```
  只列出磁盘上确实存在的产物,因此这一行反映的是该次运行所用的格式和开关。
- 清晰度报告:`<outputDir>/clarity-report.md`
- 控制台摘要(打印到 stdout),末尾是与最近一次绿色运行对比的单行结构
  delta:
  ```
  NarrativeTrace — Suite complete
    2 scenarios recorded
    Clarity: 100% high | 0% moderate | 0% low
    Reports: build/narrativetrace
    Since last green: 1 scenario unchanged · 1 changed: "Customer places order" (+1 call InventoryService.release)
  ```

失败测试的控制台报告打印的是与最近一次绿色产物对比的结构 delta ——
摘要加可读的 diff —— 而不是完整追踪,并把追踪文件链接为可点击的
`file://` URI。

## 3. 纯 Java / Agent 配置(`narrativetrace.properties`)

对于独立 Java 应用与字节码插桩 Agent,`ConfigResolver` 从 classpath 加载配置。

解析顺序:

1. 系统属性(最高)
2. classpath 上的 `narrativetrace.properties`
3. 硬编码默认值(最低)

### 属性

| 属性 | 取值 | 默认值 |
|---|---|---|
| `narrativetrace.level` | `OFF`、`ERRORS`、`SUMMARY`、`NARRATIVE`、`DETAIL` | `DETAIL` |
| `narrativetrace.packages` | 以分号分隔的包名前缀 | (空) |
| `narrativetrace.loggerName` | SLF4J logger 名称 | `narrativetrace` |
| `narrativetrace.loggingJars` | 分号分隔的 jar 文件或目录 | (空) |
| `narrativetrace.capture.resource` | `true` / `false` | `true` |
| `narrativetrace.capture.sourceLocation` | `true` / `false` | `false` |
| `narrativetrace.capture.instanceIds` | `true` / `false` | `false` |
| `narrativetrace.narration` | `off` 表示不启用 SLF4J 监听器 | （启用） |
| `narrativetrace.pipeline` | 已注册的管道拓扑名称 | （双路径） |
| `narrativetrace.pipeline.<名称>.*` | 该拓扑的设置项 | （因拓扑而异） |
| `narrativetrace.buffer.capacity` | 默认拓扑环形缓冲区的槽位数,向上取整到 2 的幂 | `65536` |
| `narrativetrace.discovery` | `off` 表示关闭扩展发现 | （启用） |
| `narrativetrace.discovery.disabled` | 以逗号分隔的提供者类名 | （空） |

### 捕获开关

`narrativetrace.capture.*` 开关扩展每个事件捕获的身份信息。它们**只控制
捕获,从不改变模式(schema)的形状**:每个受控字段在规范模式中始终可为
空,开关关闭时该字段只是缺失,因此下游消费者和跨平台夹具永远不需要按配
置分支。

- **`narrativetrace.capture.resource`**(默认开启)——在每个 span 上
  盖上自动检测的进程身份:`host.name`(取自
  `HOSTNAME`/`COMPUTERNAME`,回退到反向查询)、`process.pid` 和
  `process.runtime.version`。检测每个进程只执行一次。对主机名敏感的部
  署可以关闭。这些字段绝不会再次发射到 OpenTelemetry span 上——OTel
  SDK 的资源检测器拥有那条路径;这里只覆盖本库自身的输出(规范
  JSON、MDC)。
- **`narrativetrace.capture.sourceLocation`**(默认关闭)——在进入条
  目上记录 `code.filepath`/`code.lineno`。两条捕获路径刻意不对称:代
  理(agent)在插桩时免费烘焙被插桩方法自身的源文件和首行号,而代理对
  象(proxy)每次调用要付出一次栈遍历,记录的是*调用方*的栈帧(代理接
  口不携带行号信息)——这正是该开关默认关闭的原因。
- **`narrativetrace.capture.instanceIds`**(默认关闭)——在进入条目
  上以 `nt.instanceId` 记录接收者对象的身份哈希(小写十六进制);用于
  区分同一个类的不同实例。

自动收集在设计上保持身份形状。内容形状的上下文(订单金额、特性开关、业
务状态)绝不进入自动捕获——三层属性/MDC 富化才是客户端为不可预见上下文
准备的通道,并且它像其他值一样经过脱敏与省略。

`narrativetrace.loggingJars` 用于在类加载器看不到 SLF4J 提供者的宿主
(应用服务器)上支持代理的独立 attach:列出的每个 jar——目录会展开为其中
包含的 jar——都会在追踪启动前追加到系统类加载器的搜索路径中。路径不存在时
会在 attach 时立即失败。也可作为代理参数 `loggingJars=` 使用。

### 为事件缓冲区选择容量

尽力而为路径把事件保留在一个**固定大小的环形缓冲区**里。它从不增长:容量只
选择一次,整个环在构造时一次性分配;生产者快过排空时会覆盖最旧的槽位,而不是
扩容。没有初始容量,没有增长因子,也没有扩缩容 —— 被追踪进程为保留事件付出的
内存在启动时就已确定,并且始终如此。

`narrativetrace.buffer.capacity` 为默认的双路径拓扑设定这个大小,并向上取整到
2 的幂(环形缓冲区用掩码而非除法)。默认值是 **65,536 个槽位**。环无法接受的
取值 —— 非数字、零、负数,或大于 2^30 —— 会回落到默认值,而不是让应用启动
失败:缓冲区大小设错只会损失分析历史,而这条路径本就允许丢失它;拒绝启动损失的
却是应用本身。

**容量估算规则:**

```
容量  ≈  峰值事件数/秒  ×  可容忍的最长排空停顿
饱和时的内存  ≈  容量  ×  ~300 B/事件
```

举例说明。1,000 请求/秒 × 每请求 50 次被追踪调用 × 每次调用 2 个事件(进入与
退出)即 100,000 事件/秒。按最坏情况预留 500 ms 的排空停顿 —— 一次较长的 GC
暂停,或一个被饿死的线程 —— 峰值时会有 50,000 个事件积压。这落在默认的 65,536
个槽位之内,饱和时约占 20 MB。若流量翻倍,或你愿意承受更长的停顿,就有意识地
调大它:

```properties
narrativetrace.buffer.capacity=131072
```

占用率超过 70% 后,缓冲区选择丢弃而不是排队,并且每个被丢弃的事件都会被计数
(`EventPipeline.droppedEventCount()`)—— 相对流量而言过小的环会表现为一个
数字,而不是沉默。三种丢失方式都会计数:环覆写了消费者尚未取走的槽位、自适应
排空在超过丢弃阈值时整批丢弃,以及订阅者跟不上。

这个数字不只是可查,它还会被**宣告**。丢失过事件的捕获会把它带在树上
(`TraceTree.loss()`),每一种带页脚槽位的渲染格式都会打印一行 —— 写明数量以及
应当调高的属性:

```
⚠ Incomplete narrative: 1204 events shed under load (buffer full) — raise narrativetrace.buffer.capacity.
```

纯文本、散文与 Markdown 以页脚形式携带它(Markdown 用引用块,并在文档
frontmatter 中加上 `incomplete: true` 与 `dropped_events:`);Mermaid 与
PlantUML 以图表注释形式携带,因此图形本身不受影响。结构化 `.nt` 制品刻意不携
带它:它是审批基线,也是一致性 fixture 的格式,相同行为必须逐字节相同。没有丢
失任何东西的捕获则什么也不打印。

**为什么会有排空线程,以及什么时候才有。** 默认上下文一个都不启动:它以
`startConsumer=false` 构造消费者并按需排空,因此 `captureTrace()` 会先把环
清空再读取。你自己启动的消费者之所以拥有线程,是因为尾部情形 —— 流量停止前
最后发布的那些事件已经在环里了,而不会再有新事件把它们带出去。只在发布时顺带
排空,会让它们一直滞留到下一次可能永远不会到来的发布,所以该线程选择 park
后重新检查而不是退出,并且会一直排空到环为空为止。`close()` 会排空剩余事件,
这也正是关闭这类消费者是强制要求的原因 —— 参见
[生命周期指南](生命周期指南.md)。

```properties
narrativetrace.level=DETAIL
```

```java
var resolver = new ConfigResolver();
var level = resolver.resolve("narrativetrace.level", "DETAIL");
```

### 重复文件检测

### Agent 回退

```bash

# 使用自定义 logger 名称

# 回退到 classpath 上的 narrativetrace.properties
java -javaagent:narrativetrace-agent.jar -jar app.jar
```

## 4. Gradle 配置(`gradle.properties`)

对于 Gradle 项目,`gradle.properties` 提供了一个集中定义 NarrativeTrace 测试输出设置的位置。这里定义的属性可作为 Gradle 项目属性使用,并可转发到 fork 出的测试 JVM。

### 定义属性

输出默认就会写入;`gradle.properties` 是用来更改格式或退出的地方。在项目
根目录的 `gradle.properties` 中添加:

```properties
narrativetrace.output=false
narrativetrace.format=markdown
```

### 转发到测试 JVM

Gradle 项目属性不会自动流入 fork 出的测试 JVM。在 `build.gradle.kts` 中添加转发:

```kotlin
tasks.withType<Test> {
    useJUnitPlatform()
    listOf("narrativetrace.output", "narrativetrace.outputDir", "narrativetrace.format")
        .forEach { key ->
            (findProperty(key) as? String)?.let { systemProperty(key, it) }
        }
}
```

这会从 `gradle.properties`(或 CLI 的 `-P` 参数)读取每个属性,并将其作为系统属性传给测试 JVM。在 JUnit 的 `getConfigurationParameter()` 解析中,系统属性拥有最高优先级。

### 使用 `-P` 进行 CLI 覆盖

Gradle 项目属性可以在命令行用 `-P` 覆盖:

```bash
./gradlew test -Pnarrativetrace.format=text
./gradlew test -Pnarrativetrace.output=false
```

### JUnit 专用 DSL

Gradle 还提供了一种 JUnit 专用的方式来直接传递配置参数:

```kotlin
tasks.withType<Test> {
    useJUnitPlatform {
        configurationParameter("narrativetrace.output", "false") // 退出;默认已开启
        configurationParameter("narrativetrace.format", "markdown")
    }
}
```

这只会进入 JUnit 的 `getConfigurationParameter()` —— 它不影响 `ConfigResolver` 或 Agent。当你需要为所有集成提供单一配置来源时,请使用 `gradle.properties` 加转发的方式。

## 5. Spring 配置

使用包过滤器来控制哪些 Bean 会被纳入代理包装的考虑范围:

```java
@Configuration
@EnableNarrativeTrace
public class AppConfig { }
```

当省略 `basePackages` 时,默认为被注解类所在的包 —— 与 `@ComponentScan` 一致。若要显式收窄范围:

```java
@EnableNarrativeTrace(basePackages = {"com.example.order", "com.example.payment"})
```

### Logger 名称

当 `narrativetrace-slf4j` 在 classpath 上时,自动创建的 `NarrativeContext` Bean 会自动经由 SLF4J 叙述(`Slf4jTraceEventListener` 位于管道的同步路径上)。通过注解配置 SLF4J logger 名称:

```java
@EnableNarrativeTrace(loggerName = "myapp.traces")
```

默认的 logger 名称是 `"narrativetrace"`。设置为空字符串可禁用自动的 SLF4J 包装:

```java
@EnableNarrativeTrace(loggerName = "")
```

logger 名称还会传播到 spring-web 模块中的 `Slf4jTraceExporter`,后者将导出 logger 派生为 `<loggerName>.export`。

Spring 应用遵循自己的配置约定。推荐使用 `@EnableNarrativeTrace` 注解 —— 无需任何属性文件。

行为:

- 位于 `basePackages`(或默认包)之外的 Bean 会被跳过。
- 没有实现任何接口的 Bean 会被跳过(JDK 动态代理的限制)。
- 只追踪已配置包中的接口;Spring 框架自身的接口会被忽略。
- 会自动提供一个 `NarrativeContext` Bean。当 `narrativetrace-slf4j` 在 classpath 上且 `loggerName` 非空时,它会以该 logger 经由 SLF4J 叙述。
- 自行定义 `narrativeContext` Bean 会覆盖自动创建的那个。

关于 `@Async` 跨线程传播、Servlet 过滤器设置与生产部署模式,请参阅 [Spring 集成指南](Spring集成指南.md)。

## 6. Micronaut 配置

Micronaut 集成在 classpath 上自动发现 —— 无需任何启用注解。配置使用 `application.yml`:

```yaml
# src/main/resources/application.yml
narrativetrace:
  base-packages:
    - com.example.order
    - com.example.payment
  logger-name: myapp.traces
  service-name: order-service
  service-version: "2.0"
  environment: production
```

### 属性

| 属性 | 类型 | 默认值 | 用途 |
|---|---|---|---|
| `narrativetrace.base-packages` | `List<String>` | `[]`(空 —— 不包装任何 Bean) | 用于 Bean 包装的包名前缀 |
| `narrativetrace.logger-name` | `String` | `"narrativetrace"` | 追踪事件的 SLF4J logger 名称 |
| `narrativetrace.service-name` | `String` | `""` | 服务身份元数据 |
| `narrativetrace.service-version` | `String` | `""` | 服务身份元数据 |
| `narrativetrace.environment` | `String` | `""` | 服务身份元数据 |

### 运行机制

一个 `BeanCreatedEventListener<Any>` 会把符合条件的 Bean 包装进 JDK 动态代理。适用与 Spring 相同的筛选规则:
- Bean 的类必须位于已配置的基础包中
- Bean 必须实现已配置包中的至少一个接口
- 没有匹配接口的 Bean 保持原样

会自动提供一个 `NarrativeContext` Bean(标记为 `@Secondary`)。当 `narrativetrace-slf4j` 在 classpath 上且 `loggerName` 非空时,该上下文会接入 SLF4J 事件日志。自行定义 `@Bean NarrativeContext` 即可覆盖默认值。

### HTTP 过滤器

添加 `narrativetrace-micronaut-http` 以获得按请求的追踪生命周期:

```kotlin
implementation("ai.narrativetrace:narrativetrace-micronaut-http:0.2.1")
```

响应式 HTTP 过滤器(`HttpServerFilter`)在 classpath 上自动注册。生命周期:reset → 写入 HTTP 元数据 → 继续处理 → 捕获 → 导出 → reset。

会提供一个默认的 `Slf4jTraceExporter`(标记为 `@Secondary`)。提供你自己的 `@Bean TraceExporter` 即可覆盖。

完整集成指南请参阅 [Micronaut 集成指南](Micronaut集成指南.md)。

## 7. SLF4J 配置

**NarrativeTrace 不是一个日志框架。** 以下内容全都是接入你现有的
SLF4J/Logback/Log4j 配置——它改变的是叙述什么(自动生成而非手写),而不是
你的日志经由何种方式、发往何处、以何种形式送出。简短版见[不会取代你的日志
框架](../../自述文件.md#不会取代你的日志框架)。

通过你现有日志框架进行追踪叙述是自动的:当 `narrativetrace-slf4j` 在 classpath 上时,`PipelineBootstrap`(每个默认构造的上下文背后的组合根)会把 `Slf4jTraceEventListener` 挂到事件管道的同步路径上。无需包装类,无需接线:

```java
var context = new ThreadLocalNarrativeContext(); // 模块存在时自动经由 SLF4J 叙述
```

用 `narrativetrace.narration=off` 可以在不移除模块的情况下关闭叙述。

### Logger 名称

默认情况下,追踪事件记录在 `narrativetrace` 这个 SLF4J logger 下。要把事件路由到别的 logger,使用 `narrativetrace.loggerName` 属性(ConfigResolver 链:系统属性或 `narrativetrace.properties`),或以编程方式:

```java
var context = new ThreadLocalNarrativeContext(
    new NarrativeTraceConfig(), PipelineBootstrap.createDefault("myapp.traces"));
```

当不同的应用或模块需要各自独立的日志路由时,这很有用。logger 名称会传播到其他组件:

- **Spring Web 导出器** —— 当上下文使用自定义 logger 名称时,`Slf4jTraceExporter` 会自动派生出 `<loggerName>.export`(例如 `myapp.traces.export`)
- **Spring 注解** —— `@EnableNarrativeTrace(loggerName = "myapp.traces")` 为自动创建的上下文配置该名称
- **Agent** —— 在 Agent 参数中使用 `loggerName=myapp.traces`,或在属性文件中使用 `narrativetrace.loggerName=myapp.traces`

### 日志级别

事件在所配置的 logger 下按以下默认级别记录:

| 事件类型 | 默认级别 |
|---|---|
| 方法进入 | `TRACE` |
| 方法返回 | `TRACE` |
| 方法异常 | `WARN` |

### 自定义日志级别

自己构造监听器并把围绕它构建的管道交给上下文,即可覆盖默认值:

```java
var listener = new Slf4jTraceEventListener("myapp.traces", Map.of(
    Slf4jTraceEventListener.EventType.ENTRY, Level.DEBUG,
    Slf4jTraceEventListener.EventType.RETURN, Level.DEBUG,
    Slf4jTraceEventListener.EventType.EXCEPTION, Level.ERROR
));
var context = new ThreadLocalNarrativeContext(
    new NarrativeTraceConfig(), new DualPathPipeline(listener));
```

### MDC 字段

`Slf4jTraceEventListener` 会在每个追踪事件上设置 MDC 字段。servlet 与
Micronaut HTTP 模块中的请求过滤器还会在被追踪方法运行之前,填充请求作用域内的持久 MDC 字段。

| MDC 键 | 值 |
|---|---|
| `traceId` | 原始的 32 字符 W3C 追踪 ID |
| `traceName` | 由 `traceId` 确定性推导出的三个单词的可读名称 |
| `spanId` | 当前 Span ID |
| `parentSpanId` | 存在时为父 Span ID |
| `service.name` | 已配置的服务名称(如有) |
| `service.version` | 已配置的服务版本(如有) |
| `service.environment` | 已配置的环境(如有) |
| `host.name` | 自动检测的主机名(`narrativetrace.capture.resource`,默认开启) |
| `process.pid` | 进程 ID(`narrativetrace.capture.resource`) |
| `process.runtime.version` | Java 运行时版本(`narrativetrace.capture.resource`) |
| `nt.class` | 被追踪服务的类名 |
| `nt.method` | 方法名 |
| `nt.package` | 被追踪服务的声明包(捕获时) |
| `nt.depth` | 调用深度(顶层进入事件为 1) |
| `nt.threadVirtual` | 该条目是否运行在虚拟线程上(线程名/ID 是 `%thread` 内置项) |

`traceName` 是确定性的,但不保证唯一。精确关联请使用 `traceId`,
`traceName` 则用于提升可读性。

在 logback 的输出模式中使用这些字段,即可获得结构化的日志输出。

**外观由日志配置决定;捕获由 NarrativeTrace 配置决定。**叙事消息文本
在设计上保持简洁——除此之外的一切(追踪标识、服务标识、类、方法、深度)
都以 MDC 键的形式发布,由你的日志输出模式决定什么会出现:不含 `%X{...}`
的模式只显示纯叙事,`%X{nt.class}` 让单个键可见,JSON encoder 则为日志
聚合器输出全部键。NarrativeTrace 的设置只控制什么被*捕获*——因此什么
*可以*出现——从不控制日志行的排版。

### 与传统日志共存

结构良好的代码 —— 方法短小、命名清晰、计算结果通过返回值而非日志输出 —— 完全不需要任何 SLF4J 调用。NarrativeTrace 能从方法签名与返回值中捕获一切。

对于尚未完全按这种方式组织的代码,你可以混入传统的 SLF4J 调用,记录诸如中间计算或不体现在方法边界上的决策点之类的信息。两者会自然交织:

```java
public class DefaultOrderService implements OrderService {

    private static final Logger log = LoggerFactory.getLogger(DefaultOrderService.class);

    @Override
    public OrderResult placeOrder(String customerId, String productId, int quantity) {
        log.info("Placing order: customer={}, product={}, qty={}", customerId, productId, quantity);

        var customer = customers.findCustomer(customerId);
        log.debug("Resolved customer {} (tier: {})", customer.name(), customer.tier());

        double unitPrice = catalog.lookupPrice(productId);
        double total = unitPrice * quantity;
        log.debug("Calculated total: {} x {} = {}", unitPrice, quantity, total);

        inventory.reserve(productId, quantity);
        var payment = payments.charge(customerId, total, "tok_" + customer.id());
        log.info("Payment {} confirmed for ${}", payment.transactionId(), payment.amount());

        var orderId = "ORD-%05d".formatted(orderCounter.getAndIncrement());
        return new OrderResult(orderId, payment.transactionId(), total, quantity);
    }
}
```

```
INFO  [DefaultOrderService]   Placing order: customer=C-1234, product=SKU-MECHANICAL-KB, qty=2
TRACE [narrativetrace]        → CustomerService.findCustomer(customerId: C-1234)
TRACE [narrativetrace]        ← returned: Customer[id=C-1234, name=Alice Johnson, tier=GOLD]
DEBUG [DefaultOrderService]   Resolved customer Alice Johnson (tier: GOLD)
TRACE [narrativetrace]        → ProductCatalogService.lookupPrice(productId: SKU-MECHANICAL-KB)
TRACE [narrativetrace]        ← returned: 89.99
DEBUG [DefaultOrderService]   Calculated total: 89.99 x 2 = 179.98
...
INFO  [DefaultOrderService]   Payment TXN-00001 confirmed for $179.98
TRACE [narrativetrace]        ← returned: OrderResult[orderId=ORD-00001, ...]
```

这让 NarrativeTrace 很容易渐进式采用 —— 先与现有日志并行加入,随着你把代码重构出更清晰的方法边界,再逐步移除手写的日志调用。

### 遗留日志框架

使用 `java.util.logging` 或 Log4j 1.x 的应用:添加相应的 SLF4J 桥接([jul-to-slf4j](https://www.slf4j.org/legacy.html#jul-to-slf4j) 或 [log4j-over-slf4j](https://www.slf4j.org/legacy.html#log4j-over-slf4j)),NarrativeTrace 的输出即可原样流入你现有的日志基础设施。

## 8. TracingLevel 与 SLF4J 的相互作用

TracingLevel(第 1 节)与 SLF4J 日志级别(第 7 节)是两个相互独立的过滤层。一个事件必须同时通过两者,才会出现在日志输出中。

### 数据流

```
方法调用 → TracingLevel 过滤 → 事件管道
                                  ↓
                        Slf4jTraceEventListener
                                  ↓
                        SLF4J logger 级别过滤 → 日志输出
```

**TracingLevel** 控制什么会被**记录**进追踪树。如果一次调用在这里被过滤掉,它就永远不会到达上下文、渲染器或 SLF4J —— 它根本不存在。

**SLF4J 日志级别**控制什么会被**打印**到日志。此时事件已经捕获完成;它只影响 `Slf4jTraceEventListener` 的日志语句能否通过 logback/log4j。

### 组合示例

| TracingLevel | `narrativetrace` 上的 logback 级别 | 结果 |
|---|---|---|
| `DETAIL` | `INFO` | 完整追踪树(含参数值)进入文件与渲染器,但进入/返回日志行被抑制(它们以 TRACE 记录)。只有异常路径(WARN)会出现在日志中。 |
| `ERRORS` | `TRACE` | 只有异常路径被记录进追踪树。这些异常会写入日志(WARN 通过了 TRACE 阈值)。正常调用在任何地方都不产生输出。 |
| `NARRATIVE` | `TRACE` | 完整调用流程被记录并写入日志,但参数值显示为空字符串(NARRATIVE 抑制参数值)。 |
| `DETAIL` | `TRACE` | 全部记录、全部写入日志 —— 最大冗余度。 |
| `OFF` | `TRACE` | 什么都不记录,什么都不写日志。TracingLevel 门禁在事件到达 SLF4J 之前就拦截了所有事件。 |

### 不同目标该调哪个开关

| 目标 | 调整项 | 原因 |
|---|---|---|
| 降低日志噪音 | 提高 `narrativetrace` logger 的 SLF4J 级别 | 追踪树仍会被捕获,用于文件输出与渲染器;只是控制台/日志文件的输出量减少。 |
| 减小追踪文件体积 | 调低 TracingLevel(例如 `NARRATIVE` → `SUMMARY`) | 进入追踪树的事件更少,渲染输出随之变小。 |
| 降低 CPU/内存开销 | 调低 TracingLevel | SLF4J 级别对捕获开销没有影响 —— 代理仍会拦截、序列化并记录每一次被允许的调用。只有 TracingLevel 能省掉这些工作。 |

## 9. 各环境推荐默认值

| 环境 | 建议级别 | 建议输出 |
|---|---|---|
| 本地功能开发 | `DETAIL` | 默认已开启、`format=markdown` |
| CI 测试运行 | `NARRATIVE` 或 `SUMMARY` | 默认已开启、`format=markdown` |
| 性能敏感的生产环境 | `ERRORS`(或 `OFF`) | 不输出测试文件 |

## 10. OpenTelemetry 配置

`narrativetrace-opentelemetry` 模块提供两种集成模式。两者都要求 classpath 上有 `opentelemetry-api`(它在模块中是 `compileOnly` —— 由你自行提供)。

### 批量导出(事后)

把已捕获的追踪树导出为 OTel Span:

```java
var tracer = openTelemetry.getTracer("narrativetrace");
var exporter = new TraceSpanExporter(tracer);
exporter.export(context.captureTrace().roots());
```

适用于测试输出或请求结束后的导出。执行期间开销很低。

### 实时 Span 装饰器

从管线中的事件实时创建 OTel Span:

```java
var tracer = openTelemetry.getTracer("narrativetrace");
var listener = new OtelTraceEventListener(tracer);
// 作为同步监听器接入 DualPathPipeline
```

`OtelTraceEventListener` 是一个 `Consumer<TraceEvent>`,它从 `EnterEvent`/`ExitEvent` 事件对创建 Span,带有显式时间戳与显式的 `parentSpanId` 关联。

### Span 属性

两种模式设置相同的属性模式:

| 属性 | 来源 |
|---|---|
| `narrative.class` | `MethodSignature.className()` |
| `narrative.method` | `MethodSignature.methodName()` |
| `narrative.trace_id` | `SpanContext.traceId()` |
| `narrative.trace_name` | `TraceNamer.name(SpanContext.traceId().value())` |
| `narrative.param.<name>` | 每个参数渲染后的值 |
| `narrative.outcome` | 渲染后的返回值 |
| `narrative.duration_ms` | 节点耗时(仅批量导出) |
| `narrative.concurrency.groupId` | fork-join(分叉汇合)或即发即弃组的 ID |
| `narrative.concurrency.kind` | `FORK_JOIN` 或 `FIRE_AND_FORGET` |
| `narrative.concurrency.threadId` | 线程 ID |
| `narrative.concurrency.threadName` | 线程名称 |
| `narrative.concurrency.virtual` | 线程是否为虚拟线程 |

## 11. 扩展点

classpath 上的模块可以通过 `java.util.ServiceLoader` 扩展 NarrativeTrace，并在
`META-INF/services` 中声明。扩展分为两类，其激活方式不同。

**附加式扩展**是观察者。多个可以共存，彼此之间的顺序未定义，激活它们的正是其在
classpath 上的存在——放入 jar 就是全部安装步骤。

| 扩展点 | 接收内容 | 调用线程 |
|---|---|---|
| `ai.narrativetrace.api.spi.TraceEventListener` | 每个已发布的事件 | 发布线程（取决于拓扑） |
| `ai.narrativetrace.api.spi.ReportContributor` | 一次运行中累积的全部轨迹 | 测试运行结束时调用一次 |

`TraceEventListener` 必须是线程安全的；它挂载在何处由拓扑决定，因此即使重新配置管道，
同一个监听器也无需修改即可继续工作。两类扩展都相互隔离：抛出异常的扩展会被记录一次
并跳过，既不影响其他扩展，也不影响应用程序。

有两个退出开关用于控制发现过程，适用于不希望由 classpath 做决定的部署：

```properties
# 完全关闭扩展发现
narrativetrace.discovery=off

# 或仅关闭指定的提供者
narrativetrace.discovery.disabled=com.example.NoisyListener,com.example.SlowContributor
```

**替换式扩展**通过 `ai.narrativetrace.core.pipeline.EventPipelineFactory` 提供另一种
管道拓扑。这类扩展*绝不*因出现在 classpath 上而被激活：拓扑决定持久性，因此只有在配置
指名时才会改变：

```properties
narrativetrace.pipeline=<名称>
narrativetrace.pipeline.<名称>.<设置项>=<值>
```

未设置 `narrativetrace.pipeline` 时，将构建默认的双路径拓扑，且完全不会查找工厂。设置
之后，classpath 上必须存在响应该名称的工厂：若找不到，初始化将失败，而不会悄悄退回到
持久性保证不同的拓扑。

默认情况下，只要 `narrativetrace-slf4j` 模块存在，SLF4J 监听器就会自动组合到持久路径
上。设置 `narrativetrace.narration=off` 可保留捕获而不产生叙述输出。

## 12. 脱敏

反射式内省默认将数据视为敏感数据：DTO 到达渲染器时，就是一袋等待进入追踪、日志
和导出的字段值——手写的 `toString()` 并不能让它免于这一点，因为只要类型拥有字
段，该类型自身的字符串化表示就永远不被信任。NarrativeTrace 在两条相互独立的轴
上隐藏值，两者默认均为开启。

### 轴一 —— 字段名

与内置词表进行匹配，不区分大小写，也不区分变音符号。该词表**多语言且始终启用**
—— 没有需要选择的区域设置，也没有需要主动启用的开关。仅含英文的拒绝列表并非提供
了更弱的保证，而是提供了分布不同的保证：它只保护那些恰好用词表所用语言命名字段
的人。

| 语言 | 词 |
|---|---|
| 英语 | `password`、`passwd`、`secret`、`token`、`apikey`、`api_key`、`cvv`、`ssn`、`authorization`、`credential`、`privatekey`、`private_key`、`cardnumber`、`card_number`、`jwt`、`cookie`、`setcookie`、`set_cookie`、`sessionid`、`session_id`、`accountnumber`、`account_number`、`routingnumber`、`routing_number`、`pan`、`iban` |
| 西班牙语 | `contraseña`、`tarjeta`、`cédula`、`rut`、`cuit`、`dni`、`claveAcceso`、`claveSecreta` |
| 葡萄牙语 | `senha`、`cpf`、`cnpj`、`cartão` |
| 法语 | `motDePasse`、`mot_de_passe`、`nir`、`carteBancaire`、`numeroCarte` |
| 汉语 | `密码`、`身份证`，以及拼音 `mima`、`shenfenzheng` |

变音符号在两侧都会被规范化，因此 `contraseña`、`contrasena` 和 `CONTRASEÑA` 是同
一个模式而不是三个 —— 也包括 macOS 文件系统返回的分解形式。

多数词按**子串**匹配，因此 `userPassword` 和 `numeroTarjeta` 都会被覆盖。较短的
词则按**标识符的词元边界**匹配：

`pan` · `iban` · `rut` · `cuit` · `dni` · `senha` · `cpf` · `cnpj` · `nir` ·
`mima`

上述每一个都出现在普通业务词内部 —— `cuit` 在 `circuitBreaker` 中、`rut` 在
`truthValue` 中、`dni` 在 `midnightCutoff` 中、`senha` 跨越 `chosenHash` 的接缝
—— 而一个会清空这些字段的默认值，正是团队会彻底关闭的默认值，其结果是泄露全部
字段而非一个字段。`rutCliente`、`cuit_empresa` 和 `DNI` 仍会匹配；
`circuitBreaker` 不会。

**存疑则收窄。** 单独的 `clave` 和 `carte` 曾是这份词表里按词元匹配的词，理由与
上面的 `rut`/`cuit` 相同 —— 直到一次母语者复核发现，词元匹配只能保护一个短词不
被*别人的*复合词误伤，却保护不了代码库自己的复合词：`clavePrimaria`/
`claveForanea`（西班牙语，"主键"/"外键" —— 西班牙语数据库代码里也会写
`llavePrimaria`）和 `carteGraphique`/`carteRoutiere`（法语，"显卡"/"路线图"）
本身就是一个完整的标识符词元，旧规则同样会清空它们。这两个词已从词表中移除，
替换为真正是凭据的具体复合词 —— `claveAcceso`/`clave_acceso`、
`claveSecreta`/`clave_secreta`、`carteBancaire`/`carte_bancaire`、
`numeroCarte`/`numero_carte` —— 它们足够长，可以安全地按普通子串匹配，camelCase
和 snake_case 两种拼法都各有一条，就像 `motDePasse`/`mot_de_passe` 已经在做的
那样。

### 轴二 —— 值自身的形态

持有者令牌可能以 `value`、`header`、`data` 的名义出现，或者作为一个完全没有名字的
列表中的第三个元素，因此第二条轴询问的是字节本身在说什么。每个匹配器都是结构性
的：没有熵启发式，也没有长度规则。

| 形态 | 识别依据 |
|---|---|
| JWT | `eyJ` 前缀与三个 base64url 段 |
| 银行卡号（PAN） | 13–19 位数字，通过 Luhn 校验 |
| `Set-Cookie` | `name=value` 加上一个 RFC 6265 属性 |
| 智利 RUT | 模 11 校验位；圆点可选，**校验位分隔符 `-` 必需** |
| 巴西 CPF | 11 位数字，两位校验位 |
| 巴西 CNPJ | 14 位数字，两位校验位 |
| 西班牙 DNI / NIE | 模 23 校验字母 |
| 法国 NIR | 模 97 校验键，含科西嘉的 `2A`/`2B` |
| 中国居民身份证 | ISO 7064 校验字符*以及*一个合理的出生日期 |

各国身份证件的形态与语言无关：无论承载它的字段叫什么，CPF 就是 CPF。这正是值这条
轴适合此类证件的原因 —— 它们的字段名往往使用一种拒绝列表被阅读、却并非以之书写的
语言。

未通过校验和的相似值保持**可见**：订单号、发票号、日期。正因如此，仅有九位数字的
串不会被当作 RUT：仅凭模 11，你系统中大约每十一个九位标识符就会有一个被隐藏。

### 扩展默认值

两个开关，作用并不相同。

```properties
# 在内置词表基础上 追加（系统属性，或环境变量
# NARRATIVETRACE_REDACTION_ADDITIONALPATTERNS）
narrativetrace.redaction.additionalPatterns=betalingskort,kontonummer
```

```java
// 完全 替换 内置词表
new ValueRenderer(RedactionPolicy.ofPatterns(Set.of("ssn", "internalRef")));
```

`additionalPatterns` 面向*部署*制品的人：无需重新构建，且先读取系统属性、再读取
环境变量，而不是从 `narrativetrace.properties` 读取。`ofPatterns` 面向*编写*应用
的人。两者可以叠加：追加项仍会作用于由 `ofPatterns` 构建的策略，因为替换词表表达
的是应用对自身哪些字段敏感的判断，而不是撤销部署方所作扩展的许可。

> **追加项是子串模式**，其匹配方式与内置的子串词表完全相同。较短的追加项会带来与
> 按词元匹配的词所规避的同一个陷阱：加入 `id` 会清空追踪中的每一个标识符。

### 关闭脱敏

```java
new ValueRenderer(RedactionPolicy.DISABLED);
```

`DISABLED` 会同时关闭两条轴以及追加项。`@NotTraced` 仍然生效 —— 它是显式指令，而
非默认值。被隐藏的值渲染为字面量 `[REDACTED]`，绝不会渲染为空白，因此读者可以区
分"已隐藏"与"从未捕获"。
