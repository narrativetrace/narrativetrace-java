# NarrativeTrace Java 清晰度指南
[English](../clarity-guide.md) | [Español](../es/guia-de-claridad.md) | **简体中文**

如果追踪即代码,那么追踪的质量就是代码的质量。清晰度模块会分析你的方法名、类名和参数名,并对它们传达意图的效果进行评分。

## 快速开始

```java
var analyzer = new ClarityAnalyzer();
var result = analyzer.analyze(context.captureTrace());

var renderer = new ClarityReportRenderer();
System.out.println(renderer.render("Order Placement", result));
```

在 JUnit 5 中,当 `narrativetrace.output=true` 时会自动生成清晰度报告——无需任何代码。

## 评分内容

清晰度由五个加权组件得出一个总体评分(0.0–1.0):

| 组件 | 权重 | 衡量内容 |
|---|---|---|
| 方法名 | 30% | 动词质量、token 特异性、缩写、token 数量 |
| 参数名 | 25% | 领域特异性与泛化/无意义 token 的对比 |
| 类名 | 20% | 角色后缀质量、前缀特异性 |
| 结构 | 15% | 参数数量与调用深度的扣分 |
| 内聚性 | 10% | 方法是否与类的角色后缀保持一致 |

## 评分实践

### 方法名

第一个 token 被视为动词。领域动词得分最高,泛化动词得分最低:

| 动词类别 | 示例 | 评分 |
|---|---|---|
| 领域 | `calculate`、`validate`、`reserve`、`dispatch` | 0.60 |
| 标准 | `create`、`find`、`delete`、`update` | 0.45 |
| 布尔前缀 | `is`、`has`、`can`、`contains` | 1.00 |
| 泛化 | `get`、`set`、`process`、`handle`、`execute` | 0.10 |

像 `reserveInventory` 这样的多 token 方法比像 `reserve` 这样的单 token 方法得分更高,因为额外的 token 增加了特异性。

### 类名

类名应当带有角色后缀。设计模式后缀和功能性后缀在搭配领域前缀时得分较高:

| 模式 | 评分 | 原因 |
|---|---|---|
| `OrderService` | 1.0 | 领域前缀 + 功能性后缀 |
| `Service` | 0.0 | 没有前缀——无意义 |
| `DataProcessor` | 低 | 模糊前缀 + 泛化后缀 |
| `BookingManager` | 中 | 领域前缀,但 `Manager` 是泛化后缀 |

### 参数名

领域专属命名得分高,泛化命名得分低:

| 层级 | 示例 | 评分 |
|---|---|---|
| 领域专属 | `customerId`、`checkInDate`、`roomCategory` | 0.80+ |
| 带类型的泛化 | `id`、`name`、`count`、`status` | 0.50 |
| 模糊 | `data`、`info`、`result`、`object` | 0.10 |
| 无意义 | `x`、`foo`、`val`、`temp` | 0.00 |

### 结构扣分

参数超过 4 个或调用深度超过 5 层的方法会被扣分。每超出一个参数扣 0.1;每超出一层深度扣 0.05。

### 内聚性

方法会与类的角色后缀所对应的预期动词进行比对。`Repository` 类应当拥有 `find`、`save`、`delete`、`count` 这样的方法。`GuestRepository` 上出现 `renderReport` 这样的方法会被标记为不一致。

## 问题与严重级别

清晰度方面的缺陷会作为问题报告,并按影响程度排序:

| 严重级别 | 阈值 | 示例 |
|---|---|---|
| HIGH | 评分 ≤ 0.20 | `DataProcessor.execute(data)` |
| MEDIUM | 评分 ≤ 0.50 | `BookingManager.handleBooking(name, type)` |
| LOW | 评分 > 0.50 | 少量使用缩写 |

重复的问题(类别与元素均相同)会被去重并记录出现次数。问题按影响分(严重级别权重 × 出现次数)排序。

## 逐元素说明

问题受阈值限制——只列出低于某个严重级别切分线的名称。说明则相反:**每个元素在任何评分下都有一条通俗易懂的说明**,好名字知道自己*为什么*得分高,弱名字知道*该改什么*。一个孤零零的 0.86 不再是无从申诉的裁决。

每个方法、类、参数和 record 组件都会得到一条说明,它由评分器所用的同一批词典构建而成:

| 元素 | 评分 | 说明 |
|---|---|---|
| `OrderService.reserveInventory` | 0.95 | Domain verb 'reserve' + domain noun 'inventory' |
| `Service.processData` | 0.30 | Generic verb 'process' + vague noun 'data' |
| `OrderManager` | 0.62 | Generic suffix 'Manager' — prefer a precise role |
| `amount` | 0.50 | Broad noun 'amount' — qualify it (e.g., orderAmount) |

只要词典能够提供,说明就会给出具体指引。泛化或无法识别的动词若搭配已知的领域名词,会得到 `verbNoun` 改名提示——`Generic verb 'process' + broad noun 'order' — consider: backorderOrder, cancelOrder, fulfillOrder`——任何被扣分的缩写都会就地展开:`; spell out: chk → check`。record 访问器按名词评分标准评估,并以组件的措辞表述(`Domain-specific component 'customerId'`)。

说明绝不会进入 `issues[]`——赞扬并非需要执行的操作。它们出现在报告的 **Elements** 表以及 `clarity-results.json` 的 `elements` 数组(模式 1.2)中。

## 你自己的词汇表,来自你已有的术语表

内置词典懂得通用的软件英语。它们不知道 `fold` 在你的领域里是一个动词,不知道
`tranche` 是一个精确的名词,也不知道 `fx` 是你团队认可的缩写 —— 而它们不认识的
名称会被评为未知,而不是领域专属。

你用仓库中已有的词汇文件来教它们:已提交的 `glossary.json`(ADR-012)。没有第二
个需要同步维护的词典文件。

| 术语表条目 | 类型 | 清晰度学到了什么 |
|---|---|---|
| `settle trade` | `verb-phrase` | `settle` 是领域动词;`trade` 是领域名词 |
| `credit tranche` | `noun-phrase` | `credit` 和 `tranche` 都是领域名词 |
| `fx` | `word` | `fx` 是领域名词 |

多词术语按 token 逐个施教,因为标识符本来就是按 token 逐个评分的。所有限界上下
文都会贡献词汇:标识符不携带包名,因此评分时无法应用按上下文的作用域。

### 认可的缩写靠声明,而不是推断

术语教的是词汇,**并不**表示某个短拼写单独出现也可以接受 —— 提交短语
`calc total` 并没有说明方法是否可以叫 `calcTotal`。这个决定住在 `glossary.json`
自己的根级小节里(schema 2):

```json
{
  "schemaVersion": 2,
  "contexts": { },
  "abbreviations": { "fx": "foreign exchange", "calc": "calculate" },
  "terms": [ ]
}
```

列入其中的缩写即被认可 —— 既不会被扣分,也不会被要求拼写出来 —— 并且注释通道会
用你自己的展开来施教:`; project shorthand: fx → foreign exchange`。**未**列入的
缩写仍按内置规则处理,即便它恰好出现在某条已提交的短语里。

这一小节归人所有:采集永远不会写它,合并会原样带过。没有声明任何缩写的术语表仍
停留在 `schemaVersion` 1,其文件与从前逐字节一致。

### 术语表做不到的事

内置词典保留其权威。项目可以教会评分器一个它们不认识的词;但不能推翻它们已经认
识的词。

- **泛化动词仍然是泛化的。** 提交 `process` 或 `handle` 不会提升它们 ——
  `Generic verb 'process'` 仍会出现在说明中,方法名评分也仍会体现这一点。布尔前
  缀(`is`、`has`)同理。
- **无意义的占位符仍然无意义。** `temp`、`foo` 之类不会因为被写下来就获得意义。
- **废弃的同义词永远不是词汇表。** 别名的存在就是为了被标记出来;提升它会让它本
  该触发的 `non-canonical-term` 问题失声。
- **`stale` 术语不是词汇表。** 把一个术语标记为 stale,就是在说这个词已经离开了
  该领域。

只有*已提交*的文件才算数。某次运行采集到的内容不会反馈到这同一次运行的评分中 ——
一个会自我膨胀的词汇表会让评分变得不确定且自我认证。提交就是人工批准。

### 适用范围

| 使用面 | 如何找到术语表 |
|---|---|
| JUnit 5 扩展、JUnit 4 规则 | `narrativetrace.glossaryDir`(默认:工作目录;Gradle 插件会将其设为仓库根目录) |
| `clarityScan` | `--glossary-dir`,Gradle 插件会将其设为仓库根目录 |

读取是无条件的 —— 这与采集不同,采集需要显式开启,因为它会重写 build 目录之外的
文件。没有 `glossary.json` 的仓库,其评分与该功能出现之前完全一致;而无法读取的
术语表会带着一条警告降级为仅使用内置词典,不会让测试套件失败。

## 报告输出

### 单个场景

```java
renderer.render("Guest books a room", result);
```

生成一份 Markdown 报告,包含评分表、元素表和问题表(如果有):

```markdown
## Clarity Report — Guest books a room
Overall: 0.95 (high)

| Component  | Score |
|------------|-------|
| Method     | 0.98  |
| Class      | 1.00  |
| Parameter  | 0.90  |
| Structural | 1.00  |
| Cohesion   | 0.85  |

## Elements

| Element | Score | Note |
|---------|-------|------|
| `ReservationService.confirmReservation` | 0.98 | Domain verb 'confirm' + domain noun 'reservation' |
| `ReservationService` | 1.00 | Role suffix 'Service' |
| `guestId` | 0.80 | Domain-specific noun 'guestId' |
```

元素表会为每个场景渲染——包括高分场景——而问题表仅限于低于严重级别切分线的名称。

### 套件报告

```java
renderer.renderSuiteReport(Map.of(
    "Guest books a room", result1,
    "Legacy data processing", result2
));
```

生成所有场景的排名摘要。评分低于 0.7 的场景会获得包含各项具体问题的详细分解;每个场景——无论评分高低——都会获得一张元素表,因此没有任何评分会被略过不做解释。

## JUnit 5 集成

当 `junit-platform.properties` 中设置了 `narrativetrace.output=true` 时,JUnit 扩展会自动:

1. 对每个测试的追踪运行 `ClarityAnalyzer.analyze()`
2. 在所有测试完成后将 `clarity-report.md` 写入输出目录
3. 在控制台打印包含评分分布的摘要:

```
NarrativeTrace — Suite complete
  2 scenarios recorded
  Clarity: 100% high | 0% moderate | 0% low
  Reports: build/narrativetrace
```

无需修改任何代码——只要启用输出并运行测试即可。

## 使用 `clarityCheck` 在构建中强制执行

Gradle 插件提供了 `clarityCheck` 任务,当命名质量跌破阈值时使构建失败。这让清晰度评分成为可强制执行的规则,而不只是建议。

### 配置

```kotlin
plugins {
    id("ai.narrativetrace") version "0.2.0"
}

narrativeTrace {
    clarity {
        minScore.set(0.80)     // 任一场景评分低于 0.80 时构建失败
        maxHighIssues.set(0)   // 任一场景存在 HIGH 级别问题时构建失败
    }
}
```

### 工作原理

1. `./gradlew test`——JUnit 扩展生成 `build/narrativetrace/clarity-results.json`
2. `clarityCheck` 读取该 JSON,并将每个场景与阈值进行比较
3. `./gradlew check` 会自动运行 `test` 和 `clarityCheck`

### 失败输出

当某个场景低于阈值时:

```
FAILURE: Build failed with an exception.

* What went wrong:
Execution failed for task ':clarityCheck'.
> Clarity check failed:
    'Legacy data processing': score 0.45 < threshold 0.80
    'Legacy data processing': 3 HIGH issues (max 0)
```

### 仅警告模式

若要渐进式采用,可使用 `warnOnly` 只记录违规而不使构建失败:

```kotlin
narrativeTrace {
    clarity {
        minScore.set(0.70)
        warnOnly.set(true)
    }
}
```

### 套件级问题

属于整个运行而非某个具体场景的问题——目前是术语表采集报告的 `non-canonical-term` 词汇违规——会出现在报告的 **Suite Issues** 部分和 JSON 顶层的 `suiteIssues` 数组中。它们绝不会影响场景评分。词汇检查仅在运行前已存在提交的 `glossary.json` 时才会执行;没有术语表的项目绝不会收到套件级问题。

默认情况下套件级问题仅为咨询性质:`clarityCheck` 将其记录为警告而不使构建失败。通过 `maxSuiteIssues` 启用硬性门禁:

```kotlin
narrativeTrace {
    clarity {
        maxSuiteIssues.set(0)   // 存在任何套件级问题即失败
    }
}
```

### JSON 契约

`clarity-results.json` 文件是测试执行与 `clarityCheck` 任务之间的契约:

```json
{
  "version": "1.2",
  "scenarios": [
    {
      "name": "Customer places order",
      "overallScore": 0.85,
      "methodNameScore": 0.90,
      "classNameScore": 0.95,
      "parameterNameScore": 0.80,
      "structuralScore": 1.00,
      "cohesionScore": 0.70,
      "issues": [
        {
          "category": "param-name",
          "element": "data",
          "suggestion": "Use a domain-specific name",
          "severity": "MEDIUM",
          "occurrences": 2,
          "impactScore": 4.0
        }
      ],
      "elements": [
        {
          "kind": "parameter",
          "element": "data",
          "score": 0.10,
          "note": "Vague name 'data' — say what it holds"
        }
      ]
    }
  ],
  "suiteIssues": [
    {
      "category": "non-canonical-term",
      "element": "billing.OverdraftService.openAccountWithOverdraft",
      "suggestion": "use canonical term 'overdraft account' → rename to openOverdraftAccount",
      "severity": "MEDIUM",
      "occurrences": 2,
      "impactScore": 4.00
    }
  ]
}
```

顶层的 `suiteIssues` 数组(模式 1.1)保存套件级问题;它始终存在,运行未产生问题时为空。每个场景的 `elements` 数组(模式 1.2)在任何评分下都带有一条逐元素说明。这两项新增都是纯增量的:不含这些字段的 1.0/1.1 模式文件仍会被 `clarityCheck` 以及该 JSON 的消费方接受。

## 演示

运行酒店预订清晰度演示,查看四个质量层级下的评分:

```bash
./gradlew :narrativetrace-examples:clarity:run
```

该演示追踪四个命名逐渐变差的场景——从 `ReservationService.confirmReservation(guestId, roomCategory)`(优秀)一直到 `DataProcessor.execute(data, val)`(糟糕)——并生成一份展示评分差异的套件清晰度报告。

## NLP 组件

清晰度模块使用手工编写的 NLP,没有任何外部依赖:

| 组件 | 用途 |
|---|---|
| `IdentifierTokenizer` | 将 camelCase 和 snake_case 拆分为 token |
| `VerbDictionary` | 对 200 多个动词进行分类(领域、标准、泛化、布尔) |
| `RoleSuffixDictionary` | 对类后缀进行归类(设计模式、功能性、泛化) |
| `GenericTokenDetector` | 对 token 特异性进行分级(无意义 → 领域专属) |
| `AbbreviationDictionary` | 按三个层级为 140 多个缩写评分(通用、广为人知、有歧义) |
| `MorphologyAnalyzer` | 通过后缀(-tion、-ize、-able)识别词性 |
| `CohesionScorer` | 检查方法动词与类角色预期的一致性 |
| `ElementNoteComposer` | 将同一批词典知识转化为每个元素在任何评分下的一条教学式说明 |
| `DomainVocabulary` | 项目自己的词汇,读自已提交的术语表;在不推翻上述任何词典的前提下扩展它们 |
