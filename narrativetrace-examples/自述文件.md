# NarrativeTrace 示例

[English](README.md) | [Español](LEAME.md) | **简体中文**

这些是展示 NarrativeTrace 实际用法的可运行教程。本模块**不对外发布** —— 它的存在是为了让开发者(或 AI 智能体)能够运行一个真实场景,阅读生成的追踪,并将其与产生它的代码联系起来。

请把各子项目当作带有建议阅读顺序的教程,而不是可复用的 API。每个示例包都带有一个 `package-info.java`,其中有引导式的阅读顺序;深入某个示例时请从那里开始。

## 子项目一览

| 子项目 | 语言 | 入口点 | 教学内容 |
|---|---|---|---|
| `ecommerce` | Java | `ECommerceExample` | 旗舰示例:在真实的 Spring 服务图上进行追踪 —— Bean 接线、自动代理、SLF4J 事件日志、基于 Micrometer 的异步上下文传播,以及成功与失败场景。 |
| `clarity` | Java | `ClarityDemoExample` | 清晰度子系统如何为命名质量评分:使用一个酒店预订领域,其中的命名被刻意分为优秀、尚可与糟糕三档。 |
| `minecraft` | Java | `MinecraftExample` | 仅凭命名就能让追踪质量改变多少:同样的行为追踪两次,一次用领域专属命名,一次用泛化命名。 |
| `library` | Kotlin | `LibraryExample` | 在 Kotlin 中使用 NarrativeTrace:在一个小型图书借阅领域中,通过动态代理追踪 Kotlin 服务。 |
| `ejb4` | Java | `WildFlyAgentNarrationTest` *(Docker)* | 一个未经修改的 EJB 4(Jakarta EE 10)WAR——servlet → EJB → 服务——在 WildFly 内仅由 java 代理追踪,刻意以 EJB 2.x 时代*风格*编写;并对其时代命名生成清晰度「重命名建议」报告。 |
| `common` | Java | *(工具类,无 `run` 任务)* | 示例共享工具:`PlantUmlImageRenderer` 把生成的 `.puml` 追踪图转换为 SVG 图片;`AsciiSequenceDiagram` 把它们绘制成可在控制台显示的 Unicode 文本。 |

## 运行示例

每个示例子项目都注册了自己的 `run` 任务,并带有独立的 logback 配置:

```bash
./gradlew :narrativetrace-examples:ecommerce:run
./gradlew :narrativetrace-examples:clarity:run
./gradlew :narrativetrace-examples:minecraft:run
./gradlew :narrativetrace-examples:library:run

./gradlew :narrativetrace-examples:runExamples   # 依次运行全部四个
```

`ejb4` 没有 `run` 任务——它作为 WAR 运行在 WildFly 容器内,由带 `docker` 标签的测试驱动(见下文其小节):

```bash
./gradlew :narrativetrace-examples:ejb4:dockerTest   # 需要 Docker
```

## 演示启动器

仓库根目录提供 `./demo.sh`,是观看示例的最快方式:一条命令、没有 Gradle 噪音,实时叙述按调用深度缩进并着色,每种渲染都作为独立小节呈现。直接运行 `./demo.sh` 打开交互式选择器;`--example <名称>` 非交互运行;`--list` 列出全部示例。

**它是逐步走完,而不是一路滚过。** 在终端中,演示会在每个场景之后停下 —— `[Enter]` 继续,`q` 退出 —— 并且每个场景开头都会说明*该场景的追踪是如何配置的*:这里是通过 `@EnableNarrativeTrace` 的 Spring AOP,那里是朴素的 `NarrativeTraceProxy`,以及 `@Narrated` / `@OnError` / `@NotTraced` 中的哪一个产生了你即将读到的内容。这些说明位于 `demo/wiring.awk`,以场景标题为键;一旦某个场景失去说明,或某条说明的场景已不复存在,`demoWiringCheck` 构建任务就会失败。带停顿的运行会先完整录制、再逐段走查,因此停顿永远不会夸大追踪树报告的耗时;`--no-pause` 则实时不间断地播放整个运行,管道、CI 和 VHS 录制得到的正是这种方式。

**这些渲染从何而来**会在每次运行时讲解一次,就放在第一个渲染小节处 —— 因为这是每位观看演示的人接下来都会问的问题。没有默认渲染器,也没有任何需要配置的东西:捕获产生一个 `TraceTree`,你调用自己想要的渲染器(`new IndentedTextRenderer().render(trace)`);`NarrativeRenderer` 只有一个方法,因此你自己的渲染器就是一个 lambda。实时的 `→ ← !!` 行根本不是渲染器 —— 那是 `DualPathPipeline` 中的 `Slf4jTraceEventListener`,是唯一不需要任何渲染代码的视图。只有一个地方由配置来选择渲染器,即从测试写出的追踪文件:`narrativetrace.output=true` 加上 `narrativetrace.format=markdown|text|mermaid|plantuml`,其中 `markdown` 是默认值,Gradle 插件的 `narrativeTrace { format = … }` 设置的是同一个属性。每个小节标记都会写明产生它的渲染器。

**经典日志输出是一等公民。** 叙述本身就是普通的 SLF4J 事件流经普通的 logback,因此可以渲染为任何日志工具都能采集的传统格式 —— 完整的 `yyyy-MM-dd HH:mm:ss.SSS` 时间戳、级别、线程和 logger 名称(ecommerce 还带有 MDC `traceId`)。三处可见:

- `./demo.sh --example <名称> --classic` —— 用示例自带的 logback 配置原样运行整个示例。
- ecommerce 演示会在运行中把一个场景("未知客户")以经典格式内联展示 —— 与样式化场景是同样的事件,只是呈现方式不同。
- 普通的 `./gradlew :narrativetrace-examples:<名称>:run` 通过自带的 `logback-<名称>.xml` 使用同样的传统格式。

**翻译后的追踪同样是一等公民。** 每个示例都提交了一份领域术语表(`<示例>/glossary.json` —— 一个限界上下文,带有精心整理的西班牙语和中文翻译),`./demo.sh --example <名称> --lang zh-CN`(或 `es`)会让同一次运行经由它重新渲染:标识符和 `@Narrated` 模板以所选语言呈现,原名保留在括号中;而参数值、返回值和异常消息逐字节保持不变。交互式选择器只提供该示例术语表实际携带的语言环境。未翻译的短语汇集到"术语表缺口"页脚 —— 这是术语表补全的工作队列 —— 而命名糟糕的场景(minecraft 的未重构世界、clarity 的遗留处理)有意保持未翻译:讲不出故事的名字,也翻译不成故事。

## 示例详解

### ecommerce —— 生产风格的 Spring 应用

最完整的示例。`ECommerceExample` 运行六个场景:

1. **下单成功 + 异步通知** —— 快乐路径分叉出异步工作,以缩进文本、叙述文本和 Mermaid 时序图三种形式渲染。
2. **支付失败 —— 库存泄漏 bug** —— 追踪暴露出 `InventoryService.reserve` 被调用了,而 `release` 从未被调用:演示追踪如何揭示真实的 bug。
3. **不稳定的外部服务** —— 一个装饰器(`FlakyNotificationService`)包装真实的 HTTP 客户端(`JsonPlaceholderNotificationService`),成功一次后随即失败。
4. **未知客户** —— 输入校验类的失败分支。
5. **缺货** —— 业务规则类的失败分支,并额外通过 PlantUML 在控制台绘制为 ASCII 时序图。
6. **显式异步捕获** —— 通过 Spring 的 `ThreadPoolTaskExecutor` 上的 `CompletableFuture`,分别捕获主线程与工作线程的追踪。

关键辅助类:`ECommerceConfig`(Spring + NarrativeTrace + Micrometer 的接线)、`DefaultOrderService`(产生最有趣追踪的编排逻辑)、`ContextPropagatingTaskDecorator`(把追踪上下文带过线程边界),以及目录、库存、支付、客户、折扣、配送等简单的内存实现适配器,让追踪保持易读。

测试套件同时也是文档:`SpringIntegrationTest`(自动代理接线)、`ConcurrencyScenarioTest`(并行捕获)、`MarkdownDocumentTest`(把一条追踪渲染为带 frontmatter 的完整 Markdown 文档),以及使用 JUnit 5 扩展 `NarrativeTraceExtension` 的按服务单元测试。`NotificationServiceTest` 被标记为 `network`,因为它会发起真实的 HTTP 调用 —— 该标签默认从所有测试任务中排除。

### clarity —— 清晰度分析器奖励什么、惩罚什么

围绕酒店预订领域的四个场景,每个处于不同的命名质量档位:

1. **客人预订房间** —— 优秀的领域专属命名(`DefaultReservationService`)。
2. **经由 manager 预订** —— 尚可但表达力较弱的命名(`DefaultBookingManager`)。
3. **遗留数据处理** —— 刻意糟糕的命名(`DefaultDataProcessor`),分析器应当予以惩罚。
4. **客人仓储操作** —— 聚焦内聚性的场景。

运行完所有场景后,它把捕获到的追踪交给 `ClarityAnalyzer`,并打印 `ClarityReportRenderer` 的输出,让你能把每个评分与导致它的命名决定联系起来。

### minecraft —— 命名质量的直接对照

两个包执行相当的"玩家加入世界"工作:

- `refactored/` —— 领域专属命名:`WorldGenerator`、`PlayerInventory`、`CraftingTable`、`CreatureSpawner`、`WorldServer`。
- `unrefactored/` —— 同样的意图藏在泛化标签之后:`DataProcessor`、`StateManager`、`ThingFactory`、`EntityHandler`、`GameManager`。

`MinecraftExample` 把两者背靠背运行,便于并排比较两份追踪。它是关于命名与可观测性的教学材料,不是游戏示例。`unrefactored/**` 的测试被排除在下文的追踪输出任务之外,使生成的追踪文档只展示好的词汇。

### library —— Kotlin 使用方

一个小型图书借阅领域(`CatalogService`、`MemberService`、`LendingService`),从 Kotlin 通过 `NarrativeTraceProxy` 进行追踪,包含一次成功借书和一个抛出 `BookUnavailableException` 的失败场景,以文本、叙述文本、Mermaid 和 ASCII 时序图四种形式渲染。构建中设置了 `javaParameters.set(true)`,让真实的参数名保留到追踪里 —— 这是 Kotlin 追踪可读的前提。

### ejb4 —— java 代理下未经修改的 EJB 4 WAR

一个 EJB 4 保险理赔应用(servlet → 无状态 EJB → 服务),以刻意的 EJB 2.x 时代*风格*编写——`ClaimsProcessorBean`、`PolicyLookupEJB`、`FraudChkMgr`、
`CoverageCalcEJB`——仅针对容器提供的 API 编译,打包为 `WEB-INF/lib` 为空的 WAR:
它**不含任何 NarrativeTrace 依赖**。`WildFlyAgentNarrationTest`(带 `docker` 标签,
默认测试任务中排除)把该 WAR 部署到 Docker 中的 WildFly,仅附加
`-javaagent:narrativetrace-agent-<version>-standalone.jar`,通过 HTTP 提交一笔理赔,
并从容器日志中断言完整的叙事调用链——servlet、EJB 容器代理、bean 和服务,
连同参数与返回值。

**风格与技术。** 技术是当前的——Jakarta Enterprise Beans 4.0
(`jakarta.*`,Jakarta EE 10)运行在 WildFly 上,采用 EJB 3.x 的注解式编程模型
(`@Stateless`、`@Singleton @Startup`、无接口视图、`@EJB` 注入、没有 `ejb-jar.xml`、
没有 home/remote 接口)。只有*架构与命名*在模仿 EJB 2.x 时代的代码库;清晰度报告
吃的正是这种时代风格。这里没有 `javax.*` 命名空间或 EJB 2.x 支持;Java 8 /
EAP 6–7 服务器不在范围内(核心库是 Java 17 惯用风格;若此类客户真的出现,计划的
决策记录中勾勒了一个独立的最小记录器层)。示例证明的是:真实的应用服务器容器、
真实的容器代理、真实的 JBoss-modules 类加载——仅凭一个 `-javaagent` 标志即可叙事。

刻意的坏命名同时充当清晰度联动:`Ejb4NamingClarityTest`(普通 `test` 任务,
无需 Docker)对编译后的类运行 `ClarityScanner`,写出
`build/narrativetrace/ejb4-clarity-report.md`——「重命名建议」报告
(「Spell out: chk → check, mgr → manager」)。WildFly 陷阱由 Docker 测试装置本身固定
(完整的 `JAVA_OPTS`、精确的 `jboss.modules.system.pkgs`、等待 Undertow
上下文注册而非 `Deployed` 行)——精确设置见 `WildFlyAgentNarrationTest`。

### common —— 图表渲染工具

`PlantUmlImageRenderer` 把追踪任务产生的 `.puml` 文件转换为 `.svg` 图片,使图表输出可以在纯文本工具之外查看。它的测试资源还演示了由属性文件驱动的追踪输出(`junit-platform.properties` 中的 `narrativetrace.output=true`)。

## 追踪输出任务

每个示例子项目都拥有这些任务(定义在本目录的 `build.gradle.kts` 中)。它们在开启追踪输出的情况下运行该示例的测试套件,并把每个测试一个文件写入 `<子项目>/build/narrativetrace/`:

```bash
./gradlew :narrativetrace-examples:ecommerce:traceTests      # Markdown 文档
./gradlew :narrativetrace-examples:ecommerce:traceTexts      # 缩进文本
./gradlew :narrativetrace-examples:ecommerce:traceMermaid    # Mermaid 时序图
./gradlew :narrativetrace-examples:ecommerce:tracePlantUml   # PlantUML 时序图
./gradlew :narrativetrace-examples:ecommerce:renderDiagrams  # tracePlantUml + .puml → .svg

./gradlew :narrativetrace-examples:traceExamples             # 全部四个示例的 Markdown 追踪
```

适用于追踪任务的排除项:标记为 `network` 的测试、`MarkdownDocumentTest`(它自行管理渲染),以及 `minecraft` 的 `unrefactored/**` 测试。

## 质量门禁

示例被排除在发布流程和 JDepend 耦合门禁之外,但**并未**豁免代码质量:PMD、Spotless(Java 用 google-java-format,Kotlin 用 ktlint)、20 NCSS 的方法长度门禁以及 JaCoCo 覆盖率全部适用。只有无法单元测试的入口点(`*Example`、`PlantUmlImageRenderer`、`ContextPropagatingTaskDecorator`)被排除在覆盖率分母之外。

## 维护备注

- `common/?/`(一个名字就是问号的目录)是容器化 JVM 在 `$HOME` 未设置时泄漏出来的 fontconfig 缓存。它已被 gitignore,可以安全删除。
- 每个示例自带 logback 配置(`logback-<名称>.xml`),通过 `run` 任务的 JVM 参数接入,使每个示例的控制台输出保持可读。
- **日志记录器的配置位置。** 每个 `run` 模块都依赖 `narrativetrace-slf4j`(`build.gradle.kts`),因此
  `PipelineBootstrap` 会自动接入 `Slf4jTraceEventListener`,无需任何接线代码(配置指南
  [§7](../documentation/zh-CN/配置指南.md#7-slf4j-配置));每个 `logback-<名称>.xml` 都把
  `narrativetrace` 记录器设为 `TRACE`,这正是让你在演示中看到的 `→ ← !!` 行成为真实
  SLF4J 事件、而非仅演示专用格式的原因。`ecommerce/src/main/resources/logback-ecommerce.xml`、
  `clarity/src/main/resources/logback-clarity.xml`、
  `minecraft/src/main/resources/logback-minecraft.xml` 和
  `library/src/main/resources/logback-library.xml` 就是这四个文件。
